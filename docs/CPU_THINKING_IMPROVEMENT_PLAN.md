# 大名CPUの思考ルーティン改善方針

調査日：2026年10月5日。対象は大名家を操作するゲームAIと、その実行時間を管理する仕組み。以下の現状分析は改修前の記録。実装と性能計測の結果は [今回の実装記録](CPU_THINKING_IMPROVEMENT_IMPLEMENTATION.md) を参照。既存の [行動設計](CPU_BEHAVIOR_DESIGN.md) と [実装記録](CPU_BEHAVIOR_IMPLEMENTATION.md) を踏まえる。

## 1. 採用する方針

既存のルールと共通命令を維持し、**計測 → 重複計算と誤った候補除外の解消 → 緊急度に応じた実行管理 → 判断品質の改善**の順に進める。全面的なAI基盤の置き換えは初期段階では行わない。

思考は「戦略・作戦・部隊判断」の階層に分け、通常時は結果を保持する。宣戦・領地喪失・補給危機などの変化が起きた家だけ、必要な判断を早めに更新する。候補を安い条件で絞り、その後に経路探索などの高価な評価を行う。

8倍速の改善にはAI軽量化と時計の改修を別々に評価する必要がある。現在の時計は、AIが十分速くても日ごとの描画待ちと時間切り捨てで設定速度を下回る。AIの改善だけで「毎秒8日」を保証することはできない。

## 2. 現行コードで確認したこと

| 対象 | 現状 | 改善上の意味 |
| --- | --- | --- |
| `cpu_controller.gd::begin_day()` | 建築・経済・家臣・軍勢・郡行動・外交の更新と全国AIを同じキューに登録 | AIの選択処理と、ゲーム規則として必須の日次更新を区別する必要がある |
| `prepare_cpu_day()` | 戦略は原則7日ごと、内政は月1回を1～28日に分散。各家の戦略・軍勢の仕事は毎日登録 | 分散は実装済み。毎日の不要な仕事登録と状態収集をさらに減らせる |
| `_process()` | 仕事が完了した後に3msの経過を確認 | 3msは厳密な上限ではない。単独の探索・全国集計・家の軍勢判断が超過できる |
| `route_info()` | 全国共通で新規探索8件／日、探索時間8ms／日が目安。結果は家ごとに最大512件 | 大量の要求時に緊急撤退より通常判断が先に予算を消費し得る。1探索自体は8msで中断されない |
| `refresh_world()` / `officers_for()` | 全国の領有・部隊・外交を集計。家の武将候補を求める際にも全国部隊を参照 | 家・郡・部隊の索引と変更通知による差分更新の候補 |
| `command_armies()` | 家ごとに敵部隊と自家・同盟家の郡を照合 | 部隊数と領地数が増えるほど反復が増える。地域索引で候補を絞る余地がある |
| `route_info()` / `order_for_house()` | 評価側は到達可否・日数だけを保存し、命令側が経路を再探索 | 採用する経路を評価から命令へ受け渡すことで重複探索を減らせる |
| `attack_frontier()` / `choose_objective()` | `六角距離 × 2 + 25` で兵糧条件の候補を除外 | 同じ郡への往復なら最小1日／タイル×往復2回の安全な下界。進軍中の部隊は現在地・目標・帰郡先が異なるため区別する |
| `hex_grid.gd::path_avoiding()` | 辺の費用は一律1。探索数上限を超えると空経路 | 最短タイル数と最短所要日数は異なる。また探索打切りと本当の到達不能を区別できない |
| `game_clock.gd` | 日次キューとHUD完了後に2フレーム待ち、時間超過分と待機時間を繰り越さない | AI以外にも速度低下の固定要因がある |

保存済みの `builds/qa/cpu_release_result.json` は、CPU149家・35日・最大CPUフレーム30.8ms・検証失敗0件を記録している。ただし、手動で時計を進める確認用実行であり、現在の8倍速を実時間で測った結果ではない。保存されたEXEと現在の作業ツリーの一致も本調査では検証していない。30.8msは調査の手掛かりであり、現在のボトルネックの確定値として扱わない。

## 3. 外部資料から得た改善手法

以下の「本作への適用」は資料を踏まえた独自提案。資料の性能値を本作の改善見込みとして転用しない。

| 手法 | 資料で確認した内容 | 本作への適用 |
| --- | --- | --- |
| 階層化・共有情報 | 上位判断と下位実行を分離し、ブラックボードで情報を共有する設計 [1] | 大名の目的、戦線の作戦、個々の部隊命令を分離。脅威・余剰兵・資金・補給の情報を共用 |
| 効用値による比較 | 条件を正規化して行動を評価し、安い失格条件を先に判定する。反復を抑える時間条件も扱う [2] | 侵攻・防衛・同盟・内政を少数の評価軸で比較。合法性は共通ルールで確認 |
| 持続する行動と簡略表現 | 毎回の再選択を避け、簡略化した移動モデルで探索空間を減らす事例 [3] | 命令の継続、重要イベントでの再評価、地域単位の探索。ただし戦時の危険監視は継続する |
| 探索の実行管理 | 大量の探索を同時に保持するメモリ負担を指摘し、短い要求と長い要求を分ける案を示す [4] | 継続探索の同時保持数を少数に制限。緊急・通常の要求を分ける |
| 限定的な並列処理 | Godotの稼働中シーンツリーへの操作はスレッド安全ではない [5] | ワーカーは複製したデータの計算のみ。命令実行と状態変更はメインスレッドで行う |

資料[3]は比較的平穏な建物シミュレーションの事例であり、戦争中に周囲の変化を無視する設計まで本作へ適用しない。資料[4]は全経路のキャッシュにも注意を促しているため、経路の再利用は採用中の作戦や頻出要求に限定し、命中率・メモリ・失効頻度で採否を判断する。

## 4. 第一段階：速度低下の原因を分けて計測する

### 4.1 計測項目

`--cpu-profile` の8ms超ジョブログと最大値だけでは原因分離が不十分。以下を集計し、JSONへ出力する。ログ出力自体の負荷を避けるため通常プレイでは無効にする。

- 実時間に対する進行日数：設定1・2・4・8倍の各ケースで `進行日数 ÷ 一時停止を除いた計測秒数`。
- CPU全体と仕事種類ごとの合計時間、p50・p95・p99・最大、実行回数。
- 日付待機の内訳：必須更新待ち、AI待ち、HUD待ち、固定描画待ち。重複時間は二重加算しない。
- 経路要求数、新規探索数、展開ノード数、キャッシュ命中率、予算超過、延期、探索打切り、到達不能。
- 家ごとの待機日数とイベントから対応までの日数。全国共通予算で一部の家が長く待っていないか。
- FPS、フレーム時間、シミュレーション時間、描画負荷、AI用メモリ。軍勢移動・戦闘はAI選択とは別に記録する。

### 4.2 計測条件

同じシナリオ・セーブ・カメラ・FPS上限・VSync条件で、起動と読込を除いた実時間60秒を3回以上測る。30FPSと60FPS、平時・戦争多発・月初・部隊増加・経路失効直後を比較する。停止や計測開始時の端数は記録する。

通常AI、診断用のAI選択停止、時計の固定待ち時間だけを変えた診断実行を比較する。AI選択停止でも必須の日次更新は維持する。この比較は原因分離用であり、ゲーム機能として採用するものではない。

既存の35日テストは機能確認として維持し、実時間の倍率測定とは分ける。最大値だけで最適化対象を決めず、累積時間と長いフレームの両方を見る。

## 5. 第二段階：少ない計算で同じ判断を出す

### 5.1 共有索引と差分更新

家ごとの領地・使用可能武将・部隊、地域ごとの敵部隊を索引化する。武将の所属・配置・出陣、部隊の生成・消滅、領主・外交関係変更で関係する家だけを更新する。所持金や兵数など連続的に変わる数値は、使う時点で参照するか日次スナップショットへ反映する。

`refresh_world()` の全件再集計、郡ごとの武将候補再作成・再ソートを減らす。差分通知漏れを検出するため、開発時には定期的な全件再集計と照合する。索引の管理が実測で得になる範囲だけ採用する。

### 5.2 経路評価と命令の重複を解消

評価結果に「経路・所要日数・計算時の通行条件の版」を持たせ、採用した経路を共通命令に渡せるようにする。命令実行直前に主体、資源、開始点、目的地、通行条件を確認する。無効なら再計算し、計算済みという理由でルール検証を省かない。

キャッシュのキーには家・始点・終点・地形／道路／通行許可の版を含める。外交関係によって第三者の通行条件も変わり得るため、変更した2家だけの失効で十分か検証する。容量は件数とバイト数で制限し、全消去より期限切れ・利用頻度に応じた退避を検討する。使い捨て要求は保存しない。

### 5.3 候補絞り込みの正確さを直す

兵糧不足による早期除外には、過大評価しない所要日数の下界を使う。現行ルールなら片道の `六角距離 × 1日` が下界となる。同じ出陣元へ戻る場合の `距離 × 2 + 25` は安全であり、当初の誤除外との記述を訂正する。進軍中の部隊では `現在地→目標の距離 + 目標→帰郡先の距離 + 25` を用いる。最後の採否は、地形・道路に基づく行きと帰りの経路を別々に評価して決める。

`reachable` の真偽だけではなく、`found / unreachable / deferred / search_limit` を区別する。探索数上限や時間予算で打ち切った要求を「到達不能」として長期保存しない。再試行は既に調べた候補から続け、毎回同じ上位候補だけを調べ直さない。

同じ家で同じ日の `attack_frontier()` が重複した場合も結果を再利用する。上位3候補だけで見つからない場合は、以降の候補を次回調べる。ただし全国の全候補を毎日精査する方式にはしない。

## 6. 第三段階：緊急度と締切で思考を管理する

### 6.1 必須更新と任意の再判断を分離

経済・俸禄・補給消費・建築完了・戦闘など、ゲーム規則として必要な更新は省略しない。最新の必須状態を確定してからAI命令を適用する。通常の戦略再評価は前回の有効な計画を維持し、全AIキューの完了が常に翌日の条件になる構造を見直す。

この変更では、途中のデータで意思決定しないために日次スナップショットと命令適用順を定義する。日付をまたいだ仕事は版と予定日を持ち、適用直前に再検証する。遅延した命令をまとめて適用して、1日1回の出陣・費用支払い等の制約を破らない。

### 6.2 推奨する更新頻度の初期案

以下は調整前の設計案であり、実測済みの最適値ではない。カメラに映っているかではなく、戦争・補給・外交の状態で頻度を決める。

| 判断 | 更新の契機 | 初期案の締切・頻度 |
| --- | --- | --- |
| 宣戦・自領侵入・同盟参戦要請 | 対象家へのイベント | 次の命令適用機会、遅くとも次の日次境界で再評価 |
| 補給危機・大量損耗・帰郡先喪失 | 閾値を越えた時、毎日の安い監視 | 遅くとも翌日。補給猶予から締切を短縮する |
| 進軍中の通常部隊 | 到着・命令完了・目標失効 | 命令を継続。危険監視は毎日 |
| 戦時の作戦見直し | 戦線変化と定期更新 | 1～3日ごと |
| 平時の侵攻・同盟評価 | 関係・戦力の変化と定期更新 | 原則7日ごと |
| 人事・建築・研究 | 空席・完成・不足・忠誠危機 | 通常は月1回を分散し、危機だけ前倒し |

家IDと予定日で処理を分散する。イベントが集中しても、同じ家・同じ判断の仕事は重複登録しない。待機期間が長い仕事の優先度を上げ、緊急要求にも家ごとの公平性を設ける。

### 6.3 大きな仕事の中断・再開

全国集計、家の複数部隊判断、候補経路探索を、処理位置を持つ小さな仕事へ分割する。1フレーム3msを初期目安として維持しつつ、仕事ごとに処理件数・展開ノード数で中断できるようにする。不可分な命令の検証・実行は短い単位へ限定する。

経路探索は優先キューに登録し、進行中の探索状態はまず1～2件程度に制限する。緊急用と通常用の枠を設け、古い要求を放置しない。途中状態を大量に保持する方式は資料[4]の注意に従って避ける。

実時間予算だけで採用する判断を変えると、PC性能やFPSにより結果が変わり得る。判断順・同点処理・論理上の締切を固定し、必要な場合はノード数等の決定的な予算を併用する。実時間は主にフレームへの配分に使い、性能差で有利不利が偏っていないか検証する。

## 7. 第四段階：戦略判断の質を改善する

### 7.1 階層と評価軸

大名の戦略目的は防衛・侵攻・同盟形成・復興などに絞る。その下に出陣元・目標・集合地点・帰郡先を持つ作戦を置き、部隊は作戦の範囲で移動・交戦・撤退を決める。全部隊が独立に同じ目標を選び直す方式を避ける。資料[1]の階層化・共有情報をこの形で適用する。

既存の戦力比条件や合法性は入口の条件として残す。通過した候補の比較に、資料[2]を参考にした効用値を導入する。侵攻なら戦力余裕・往復補給・郡の価値・自領防衛への負担、同盟なら共通脅威・援軍可能性・友好度・費用、内政なら不足解消と投資回収を用いる。

値の範囲を揃え、似た評価軸の二重加点を避ける。採用・不採用の理由と項目別の点数をログに残す。効用値自体がAIを軽くするとは限らないため、候補数と高価な評価を制限する。

### 7.2 目的の継続と複数部隊の協調

目標の有効期限、切替に必要な点差、再判断までの最低期間を設ける。わずかな変化による侵攻先・同盟先の振動を抑える。宣戦、補給危機、目標喪失は継続条件より優先する。

作戦が必要兵力と到着見込みを持ち、目標ごとに部隊を予約する。十分な兵が割り当てられた目標への追加投入を抑え、自領防衛と他戦線へ回す。単純な国全体の兵力だけでなく、到着できる兵力と補給を評価する。指揮官の能力や性格による重みは、共通判断が安定してから追加する。

### 7.3 地形・道路に合った経路評価

現行の一律辺費用を、実際の移動日数を使う重み付き探索へ改める候補を評価する。ヒューリスティックには過大評価しない下界を使う。経路選択が変わるため、単なる性能修正とは分けてゲームバランスを確認する。

長距離探索が実測で支配的なら、地域や連結領域を上位グラフにして候補経路を作り、六角形で詳細化する。通行条件や道路変更に追従し、上位グラフの近似で有効経路を失わないよう詳細探索へのフォールバックを設ける。資料[3][4]の探索空間削減を参考にする。標準的なJPSを、六角形・地形別費用・動的通行条件へそのまま適用しない。

## 8. 8倍速の時計と並列化の扱い

時計改修では、日次状態の確定と、毎日の画面描画待ちを分ける。1フレームで複数日の更新を順番に実行しても、日次イベントを欠落させず、途中で必須更新待ちになったら止める。HUDは最後の確定状態を表示する。前の仕様に合わせた `test_day_barrier.gd` 等は、新しい順序保証を検証する形へ更新する。

経過時間を端数として保持する案を検討するが、無制限な追いつき処理は導入しない。1フレームの処理量とバックログを制限し、停止・最小化・アプリ復帰中の時間は別に扱う。処理能力不足時には実進行率が落ちることを計測できるようにする。通常負荷で毎秒8日に近づくことと、過負荷時の操作性の両方を評価する。

マルチスレッド化は、索引・探索・実行管理を直した後、純粋な計算がまだ重い場合に限定する。読み取り専用スナップショットをワーカーへ渡し、評価結果をメインスレッドで版確認して適用する。Node、稼働中のシーン、共有Dictionaryへワーカーから直接変更を加えない。Godot公式資料[5]を前提とし、本プロジェクトで使うエンジン版でも確認する。

## 9. 実装順と完了条件

| 優先度 | 作業 | 完了条件 |
| --- | --- | --- |
| P0 | 実時間の倍率・仕事別時間・待機理由を計測 | AIと時計と描画の寄与を区別でき、比較用の記録がある |
| P1 | 誤った距離除外と探索状態の区別、重複探索削減、索引 | 道路経路を誤除外しない。打切りを到達不能にしない。探索数と累積時間が減る |
| P2 | 必須更新分離、優先度・公平性、仕事の中断再開 | 緊急命令が通常思考に埋もれない。長い単独仕事が減り、保留が期限内に処理される |
| P3 | 時計の固定待ちと端数保持を見直す | 日次更新を欠落させず、実時間進行率と操作性が改善する |
| P4 | 階層化、効用値、作戦共有、重み付き経路 | 防衛・補給・援軍の行動品質が改善し、思考コストの増加が予算内に収まる |
| P5 | 必要に応じて地域探索・ワーカー計算 | 実測で効果があり、メモリ・結果適用・保存再開に問題がない |

初期の性能目標案は、基準PC・60FPS・通常負荷・固定カメラで8倍設定の実進行率7.6～8.0日／秒、AI実行時間p95が3ms以内とする。これは達成値ではなく、P0の測定で妥当性を確認する目標。過負荷条件には同じ値を保証せず、イベント対応遅延・最大フレーム時間・待ち行列の増加を別に評価する。

1・2・4・8倍の同じゲーム日付で、処理済み日次イベント数と支払回数を比較する。意図した判断変更以外の差が出たら、処理順や締切を調べる。

## 10. 検証と保存の要件

- 既存のCPU・外交・軍勢・日次境界テストを回帰確認に使う。新しいテストは、経路打切りと到達不能の区別、道路のある遠距離候補、緊急撤退の優先、長時間待つ家、失効した経路、日をまたぐ命令の二重適用に絞る。
- 30・60FPSと各倍率で実描画の計測を行う。ヘッドレスの結果だけで描画待ちの解消や操作性を判定しない。
- 同じセーブの長期進行で、兵糧切れによる損耗、目標変更回数、同盟防衛の反応、建築・研究の停滞、家ごとの対応遅延を比較する。勝率だけでAI品質を判断しない。
- 現行形式のセーブには目的・作戦・予定日・未処理命令等の再開に必要な論理状態を保存する。途中探索は再要求可能な形にし、ワーカーそのものは保存しない。読込後も支払・出陣・参戦を二重実行しない。
- リリース前の方針に従い、旧セーブとの移行・互換性チェックは追加しない。変更後の現在形式で保存・読込を確認する。
- ゲーム機能やUIを実装変更した段階で `python tools/export_windows_release.py` によるWindowsリリース版の書き出しと起動を確認する。本書作成は文書のみのためビルド対象の変更はない。

## 11. 今回は先行導入しない手法

GOAP・HTNや深いゲーム木探索への全面移行、強化学習、LLMによる実行時思考は初期の改善対象にしない。現在の問題に対して、計測・重複削減・実行管理より大きな設計と検証コストがかかるためである。複雑な作戦を少数のルールで表せなくなった時に、局所的な計画探索を改めて比較する。

CPU予算を一律に増やすこと、画面外の家だけ思考品質を落とすこと、全国AIの日次更新を無条件に省くことも先行策にしない。判断の公平性とゲーム規則を保ちながら、不要な計算と固定待ち時間を減らす。

# 地形の区画化・読み込み・解放・近景再利用

実施日：2026年10月2日。[軽量化調査](MEMORY_CPU_OPTIMIZATION_RESEARCH.md)と[先行実装の結果](MEMORY_CPU_OPTIMIZATION_RESULTS.md)に続く地形処理の変更。

その後、平坦部と遠景の頂点間隔を広げる試行を実装した。[平坦部・遠景の間引きの結果](ADAPTIVE_TERRAIN_OPTIMIZATION_RESULTS.md)を参照。以下は均一間隔の区画化時点の記録。

## 実装

- 全国の遠景メッシュを1,024×1,024ワールド単位の64区画に分割。頂点間隔は従来の16を維持する。各区画は65×65頂点。境界の頂点を共有位置で複製し、周辺の高さを参照して法線を計算するため、形状・照明の継ぎ目は変わらない。
- カメラの視錐台と地形の高さから必要な区画を判定する。画面内へ影を落とせる画面外の区画も保持し、それ以外はノード・メッシュの参照を解放する。画面に戻る区画は制作時に保存した小さなメッシュから読み込む。通常実行では全国一枚の遠景メッシュを併せて保持しない。
- 遠景の読み込みは区画単位の同期処理とした。次の描画に地形が間に合うため、素早い回転で地面が欠けることを防ぐ。一方、新しい区画の読み込み時には停止時間が生じうる。
- 近景の512×1,024領域を128×128の32区画に分割。頂点間隔2、元の高さ・法線・UV・外周の遠景への補間を維持する。移動後も同じ形状の区画はメッシュと描画ノードを再利用する。
- 外周の補間状態をキャッシュのキーに含める。新しく必要な区画と、外周に出入りして形状が変わる区画だけ生成する。128単位の横移動では32区画中8区画を再利用し、最大24区画を生成することを確認した。同じ位置での回転では近景を再生成しない。
- 近景の生成は既存CPUジョブ管理を使い、同時2件、1件あたり384 KiBを予約する。完成前に不要になった結果はGPUへ送らず破棄する。キャッシュは最大64区画を基本とし、表示中・切り替え待ちの区画を優先する。全区画が揃ってから領域を切り替え、途中の穴と継ぎ目を防ぐ。
- 近景が不要な倍率では近景メッシュ・キャッシュを解放する。表示範囲が変わらないフレームでは区画一覧の再計算を省く。

元の地形標高データはクリック・遮蔽判定・近景生成に必要なため保持する。富士の専用高精細メッシュ、画像解像度、素材、影設定は維持した。全国メッシュも比較試験と入力不一致時の従来処理への復帰用としてファイルには残す。これは通常実行で全国メッシュを読み込むことを意味しない。

## 確認

- 地形・影の画素比較：800%の3地点×回転4方向と全国表示の計13画面で、従来の一枚メッシュと区画版の1920×1080画像が完全一致。描画時間を固定して比較した。すべての視点の数学的保証ではない。
- 近景の135,200頂点について、従来領域の頂点位置・UVを一致確認。GPU用メッシュにした後の法線も誤差1e-6未満。区画境界の複製頂点も含めた数値。
- 近景の再利用、生成数、画面外遠景の解放、回転時の生成抑止、低倍率でのキャッシュ解放を自動確認。
- 視点角・ズームの固定点、富士の表示、回転、480件の地形レイ判定の回帰試験に合格。
- Windowsリリース版の書き出しに成功し、実行ファイルで800%の移動・回転試験を実施。書き出したPCKでも区画の読み込み・再利用試験に合格。

画素比較の記録：`builds/performance_800/chunk_culling/report.json`。

## 測定結果

**区画の保持・生成対象は減ったが、800%での移動・回転中の60fpsは未達成。今回の区画化だけでfpsやプロセス全体のRAMが改善したとはいえない。**

Windowsリリース版、Godot 4.7.2 Compatibility、1920×1080、800%、視点角15度、最大60fps。CPUはi7-12700F、GPUはRTX 4060。日付進行を止め、素材読み込み後の各区間120フレームを計測した。移動は半径160の円、回転は360度。従来処理は `--legacy-terrain` で実行し、続けて区画版を実行した単回の比較。計測のばらつきがある。

| 地点・操作 | 従来fps | 区画版fps | 従来p95フレーム時間 | 区画版p95フレーム時間 |
|---|---:|---:|---:|---:|
| A 移動 | 28.96 | 29.34 | 48.90 ms | 48.75 ms |
| A 回転 | 22.07 | 21.91 | 93.73 ms | 98.49 ms |
| B 移動 | 23.38 | 22.79 | 66.16 ms | 67.97 ms |
| B 回転 | 24.63 | 24.02 | 62.20 ms | 58.64 ms |
| C 移動 | 38.73 | 38.39 | 36.20 ms | 29.85 ms |
| C 回転 | 28.42 | 27.43 | 79.38 ms | 82.92 ms |

静止は両方式とも3地点で60fps。A=(4480,5504)、B=(4768,5440)、C=(5500,4100)。生ログの識別ラベルはkinki／fuji／kanto。実時間で一定速度の巡回や、多数部隊が活動する最悪条件の保証ではない。

区間末の遠景保持数は17～27区画、71,825～114,075頂点。従来の全国メッシュ263,169頂点から、保持する遠景頂点が約57～73%減った。ただし、影のため保持する区画も含む数であり、フレームごとのGPU頂点処理時間を直接測った値ではない。近景の境界では頂点を複製し、メッシュ数と描画呼び出しも増える。

| プロセスのピーク使用量 | 従来 | 区画版 |
|---|---:|---:|
| Working Set | 1,412.8 MiB | 1,479.8 MiB |
| Private Commit | 3,183.2 MiB | 3,113.7 MiB |

Private Commitは約2.2%減った一方、Working Setは約4.7%増えた。OSの常駐管理、画像、描画先、ドライバーも含むため、地形の削減だけから総RAM削減を断定しない。近景の64区画キャッシュは旧方式の2領域と頂点数が近く、キャッシュ全体を大幅に小さくする変更ではない。

WindowsのプロセスCPU時間から求めた区間平均でも一貫したCPU削減は見られなかった。例としてA回転は2.15→2.80コア相当、C移動は1.78→1.49コア相当。1コア相当はCPU時間1秒／実時間1秒を表し、20論理プロセッサ全体に対する使用率ならそれぞれ20で割る。生成の並列数と区画数の調整は行ったが、影を含む描画呼び出しや移動時の地図更新も引き続き改善対象になる。

生データ：`builds/performance_800/chunks_legacy_paired.json`／`chunks_final_release.json`、各 `_process.json`。画質維持と区画再利用は確認済みだが、速度向上の保証としてこの変更を評価しない。

## 主な変更箇所と再生成

- `scripts/map/terrain_chunk_set.gd`：区画の判定、読み込み、解放、近景生成・再利用。
- `scripts/map/map_view_3d.gd`：区画の導入、外周補間を含む共通の形状生成。
- `data/derived/elevation/terrain_chunks/`：64区画の制作済みメッシュと入力ハッシュを含むマニフェスト。
- `tools/godot/build_terrain_meshes.gd`：標高データを変更したときの制作済みメッシュ生成。
- `tests/base_map/godot/test_terrain_chunks.gd`：形状、再利用、解放。
- `tests/base_map/godot/test_terrain_chunk_culling.gd`：従来のメッシュとの画素比較。

標高データや地形メタデータを変更した後は、次のコマンドで区画メッシュも再生成する。

```powershell
godot_console --headless --path . --script tools/godot/build_terrain_meshes.gd
```

入力ハッシュが一致しない場合は従来の地形処理に戻り、古い制作済み区画を使用しない。制作後はWindowsリリース版を再書き出しする。

# マップ描画の軽量化案・Android対応に向けた優先順位

実装後の状況は [軽量化の実装・検証結果](MAP_PERFORMANCE_RESULTS.md) を参照。以下は実装前にまとめた計画と観測記録。

2026-09-12。対象は道路を実線化した現行版。今回はコードと資産を調査し、改善案をまとめた段階であり、実装・描画設定・ビルドは変更していない。

最初に取り組むのは、**メモリの上限管理、移動時の同期読み込みの解消、実行時のメッシュ生成の削減**。8192×8192の論理座標、400%ズーム、709区画、道路・拠点・境界の元データを保ちながら、画面に必要な表示用データだけを扱う構成へ進める。

## 観測と、まだ分からないこと

ユーザー報告はメモリ約8GB、CPU約10%、頻繁なフリーズ。今回の読み取り時点では、起動中の `windows-solid-roads/MyWorldsOnFreedom.exe`（PID 22272）のワーキングセットが約1.525 GiB、Private Bytes相当が約2.756 GiBだった。これは別時点・別指標の一回の観測であり、8GBのピークを否定したり再現したりする結果ではない。GPUの専用・共有メモリ、操作中の一時的ピーク、長時間の増加は未計測。

CPUの合計10%だけでは余裕があると判断できない。複数コアの合計では低く見えても、描画を進めるスレッドが待機・計算で止まる場合がある。平均FPSだけでなく、一番遅いフレームと停止した関数を調べる。Godotも継続的な低速、突発的な遅延、ロード時の遅延を分けて計測する方法を説明している。[公式の計測・最適化指針](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html)

## コードから確認できた負荷の候補

|道路データの重複用途|道路の共有描画データとは別に、注記用レイヤーも全segmentsを走査する。投影・領域抽出・注記の役割を整理する余地がある。|[shared_road_layer.gd](../scripts/map/shared_road_layer.gd:15)、[road_connection_layer.gd](../scripts/map/road_connection_layer.gd:30)|

すでに「全部を同時に描かない」処理はある。新規に空間索引を一から追加すれば解決する、という状況ではない。読込単位、生成タイミング、キャッシュの容量、選択時に全域メッシュを作る処理が主な改善対象になる。

## メモリについての具体的な手掛かり

- 拡大用タイルは211枚、各1032×1032。確認した全211枚のインポート設定は `compress/mode=0`、GPU圧縮ではない。RGBA8・ミップなしと仮定すると1枚約4.06 MiB。実際の形式・ドライバ上の保持量は別途測る。
- 旧背景タイルは41枚、各2048×2048。可視タイルでは背景・陰影・海岸の3画像を読む。3枚ともRGBA8と仮定した場合は1タイル48 MiB。全41枚を常に読み込んでいるという意味ではない。
- 詳細地形のJSONは全国合計約1.96 MiB。これだけで8GBを説明するのは無理がある。全体を大雑把に「巨大な地形JSONが原因」と扱わない。
- 郡表示ディレクトリのJSONは調査時点で約81.17 MiBあるが、集計には台帳やレポートも含む。起動時に全部を読んでいるわけではない。国別geometryの大きいものは約3 MiB、起動時indexは約0.75 MiB。
- 起動時に読む道路接続JSONは約6.04 MiB、共有道路約1.53 MiB、水系約7.00 MiB。JSONをDictionaryやArrayへ展開したメモリ量はファイルサイズと一致しない。
- 旧背景41タイルの地形頂点・UV・索引を全て両表示モードで保持した場合、数値バッファの単純合計は約100.4 MiB。生成中の配列やGPUのコピーを除く概算で、現状の保持実測ではない。

したがって、8GBを一つの要因で説明するのではなく、CPUメモリ、GPUメモリ、読込中の一時領域、解放されない参照を分けて記録する必要がある。

## 改善の優先順位

|順番|実施内容|期待する効果|注意点・確認方法|
|---|---|---|---|
|0|操作別の計測を追加|停止する場所と8GBの内訳を絞る|読み込み・JSON解析・投影・メッシュ生成・GPU登録を別に計時。全国→近畿→400%→郡選択→立体切替を固定ルートで測る。|
|1|全キャッシュにバイト単位の上限を付ける|全国を移動しても常駐量が一定範囲に収まる|背景、投影線、郡メッシュを別予算で管理。古い項目を排出し、必要な項目を毎フレーム捨てて読み直す状況を防ぐ。|
|2|読み込みと表示反映を分離する|移動・ズーム時の長い停止を減らす|バックグラウンドで読込・数値整形、画面への反映は短時間に分割。準備中は直前の低精細地図を表示。古いカメラ位置への要求は破棄する。|
|3|地形・郡メッシュを事前生成する|起動、郡選択、平面／立体切替の処理集中を減らす|配布用のPacked配列・索引付きメッシュに変換し、floatを1個ずつ読んで投影する処理を外す。元の編集用JSONは残す。|
|4|テクスチャのGPU圧縮と表示密度の段階化|画像の常駐量・転送量を減らす|地形の色・陰影を対象に比較。Androidは現行Compatibility構成でETC2を先に検証。文字・境界・クリック用データは圧縮で曖昧にしない。|
|5|表示更新を変更時だけにする|静止時のCPU使用・電力消費を減らす|カメラ、ズーム、画面サイズ、表示切替、データ到着時だけ更新。移動中もタイル領域を越えるまで一覧取得を省く。UIと描画は更新理由を分ける。|
|6|国単位から一定サイズの表示区画へ分割|大きい国や郡でも必要な部分だけロードできる|背景と同じ空間索引を利用。面、共有線、クリック候補、塗りを区画ごとに読み、同じ境界を二重描画しない。詳細出典は選択時に読む。|
|7|地形・線のLODを追加|全国表示とAndroidの頂点・描画負荷を減らす|全国では粗い地形を使い、拡大時は細かくする。共有辺を同じ規則で簡略化し、国境・郡境・海岸・塗りのずれを防ぐ。|
|8|必要な箇所だけネイティブ処理・GPU投影を検討|残った大きい計算負荷を下げる|先に上記の構造改善を測る。全体をC++へ書き換えたり描画方式を全面交換したりしない。|

同期 `load()` は実行スレッドを止める。`load_threaded_request()` と完了確認を使えば待ちを分離できるが、未完了のまま `load_threaded_get()` を呼ぶと再び停止する。JSON読み込み・配列加工は別途ワーカー側の処理が必要になる。[公式のバックグラウンド読込](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html)

スレッド化は「全てを別スレッドに移す」という意味ではない。SceneTreeへの追加、共有リソースの変更、描画リソースの更新は使用APIの制約を守り、数値処理と画面への反映を分ける。同時ロード数も制限してメモリのピークを抑える。[公式のスレッド安全性](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)

PNGやZIPのファイル容量を小さくするだけでは、GPU上のメモリ削減にはならない。GodotのLossy画像圧縮もGPU使用量を減らさない。GPU圧縮は画質との比較が必要で、現行Compatibilityでは高品質ASTCの指定だけで解決しない。ミップマップも容量を増やすため一律に有効化しない。[公式の画像インポート・圧縮](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_images.html)

## 地図の見た目を保つ方針

論理座標8192×8192とズーム400%は変更しない。拡大中に全域を高精細で持つのではなく、画面内と小さな余白だけを高精細にする。移動中は低～中精細、停止したら高精細へ更新する方式を候補とする。

最初の改善では、道路・国境・郡境の形状や地表16単位の整合性を変えない。事前生成、Packed形式、不要な更新の停止、キャッシュ制限を先に行う。後段で地形格子を粗くする場合は、線の投影・塗りの分割・逆変換の関係をまとめて検証する。地形だけを粗くすると、現在守っている地表と線・面の一致を崩すためである。

JSONは編集正本として維持し、実行時に必要なデータだけを専用形式へ変換する。細かい出典台帳や、古い合併前の未参照ファイルを配布物から省くこともできる。ただし、配布容量の削減と実行時メモリの削減は別の成果として測る。

## Androidで目指す状態（暫定目標）

端末指定がないため、まずRAM 6GB程度の中級機を基準候補とする。以下は実測済みの性能やOSの保証値ではなく、端末を決めて検証するための目標案。

|指標|初期目標案|
|---|---|
|フレームレート|操作中30 FPSを安定させる。対応端末では60 FPSを選べる。|
|フリーズ|通常操作で100ms超の停止をなくすことを目標にし、特に連続500ms超を優先して除去。冷起動・初回ロードは別計測。|
|メモリ|ゲーム全体のPSSを通常512 MiB程度、ピーク768 MiB以内を目標案にする。GPU等の共有分を重複加算しない。|
|キャッシュ予算|地図画像96～128 MiB、表示メッシュ・投影線64 MiB前後、読み込み中の一時領域32～64 MiBを初期案として実機調整。これらは上記総量の内訳。|
|待機時|カメラ静止中の地図計算をほぼ止め、表示・入力・必要なUIだけ更新する。|
|長時間動作|同じ巡回を繰り返してもメモリが増え続けず、15～30分の操作で発熱後の速度低下も許容範囲に収める。|

Androidには専用の画質プリセットを設ける。拡大用ラスタの密度・先読み枚数・描画フレーム数を下げても、座標とズーム上限、地名・道路・郡の内容は共通にできる。起動しただけで成功とせず、400%表示・長距離移動・郡選択・立体切替を実機で測る。

## 実装する場合の区切りと合格条件

1. **計測版**：OS側のメモリ、Godotの描画資源、FPS、フレーム時間p50/p95/p99/最大、100ms超の回数、タイル数、キャッシュのバイト量を記録する。WindowsのWorking SetとPrivate Bytes、AndroidのPSSを同一指標として混ぜない。
2. **負荷を抑える小規模修正**：更新条件、キャッシュ上限、読込要求の重複防止、同時ロード数、使わない注記処理を整理。同じ固定ルートで前後比較する。
3. **停止を避ける読込経路**：バックグラウンド読込、事前生成メッシュ、読み込み中の表示を追加。フレーム時間を測ってメインスレッドへの反映量を制限する。
4. **メモリ削減版**：画像圧縮、表示区画の分割、出典の遅延ロードを追加。タイル境界の往復で読み直しが増えすぎないことも検査する。
5. **Android検証版**：平面・立体、全国～400%、道路選択、仮称領域を含む郡選択を実機で連続操作。低メモリ時・バックグラウンド復帰・発熱後も確認する。

各段階では同じ入力データと同じ操作ルートで比較し、速度の改善と引き換えに境界、クリック判定、地表塗り、名称、経路が壊れていないことを確認する。既存の起動・表示テストは機能確認として活用し、長時間の性能検証を別に追加する。これまでの短い起動確認は、8GBのピークや長時間フリーズがないことを保証するものではなかった。

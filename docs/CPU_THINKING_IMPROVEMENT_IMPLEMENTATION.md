# CPU思考・進行時計の改善実装

対象：[改善方針](CPU_THINKING_IMPROVEMENT_PLAN.md)。実装日：2026年10月5日。

## 採用した変更

| 項目 | 実装 |
| --- | --- |
| 計測 | `--cpu-profile` で仕事別・CPUフレームの時間分布、探索要求・命中・ノード数、論理待機日数、時計の待ち理由を収集。軍勢の日次処理は補給・制圧・統治・通知等へ内訳を追加 |
| 索引・重複削減 | 出陣中武将・家別軍勢・外交関係・地域別軍勢と奉行所を索引化。戦力は必要な家だけ日ごとに計算。郡奉行任命の全国再集計は同一フレームでまとめ、保存前に確定 |
| 経路の共有 | 最短所要日数の経路、主体・始点・目標・通行条件の版を評価結果に保存。共通命令で検証して再利用。外交・所有・道路変更で失効。キャッシュ上限は全国512件／概算2MiB、利用から90日 |
| 経路探索 | 地形と道路の実移動日数を使う重み付きA*。`found / unreachable / deferred / search_limit` を分離。打切りを到達不能として保存しない。候補の続きは目的別カーソルで管理 |
| 探索の並列化 | 計測で探索待ちが支配的だったため採用。読み取り専用の地形・道路・障害物スナップショットだけをWorkerThreadPoolへ渡す。通常・軍事・緊急の優先順位で、進行中と失効済み未終了を合わせて最大2探索、未着手は最大64件。Node・シーン・命令はメインスレッドのみ |
| 思考の実行管理 | 必須日次更新を先に確定。通常再判断は日をまたいで継続し、同一仕事を重複登録しない。緊急判断と3日待った仕事・探索は日付進行の条件にする。部隊判断を1部隊単位へ分割。探索完了はそれを要求した判断だけを再開 |
| 判断品質 | 侵攻は戦力余裕・人口・距離、同盟は戦力・友好度・距離を正規化。採用時の点数を記録。既存の兵糧・戦力比・合法性を維持。目標継続の加点、作戦の出陣元・集合元・帰郡先・到着見込み・必要兵、目標への兵力予約を追加 |
| 時計 | 毎日の固定2描画フレーム待ちを廃止。超過時間を最大2日分保持し、1回最大4日を順序どおり処理。必須状態確定前に軍勢移動・戦闘を実行しない。停止・最小化・アプリ中断中の追いつきを抑制。HUD完了は日付の障壁にしない |
| 保存 | 現行形式26へ変更。時計バックログ、予定日・優先度付き仕事、候補カーソル、作戦を保存。途中探索とワーカーは保存せず読込後に再要求。旧形式の移行は追加していない |

CPUのメインスレッド予算はフレーム間隔の18%、最小1.5ms・最大6msとした（60FPSで約3ms、30FPSで約6ms）。固定3msでは30FPS時の実時間あたり予算が半減し、予備計測で締切待ちが増加したため、索引・探索の最適化後に調整した。個々の共通命令と日次規則は不可分なので、これは厳密な上限ではない。領地制圧時の所属・境界更新や月次処理は長いフレームを発生させ得る。進行倍率の表示には、処理負荷により目標速度を下回る旨を追加した。

長い実時間計測で、当主未記録（`ruler = null`）の家による制圧が所属更新の途中で停止する既存不具合も判明した。郡・城・郡内施設の当主欄をnullのまま更新できるよう修正し、制圧テストへ追加した。作戦の到着予定日もJSON読込後に整数へ戻し、保存前との論理状態一致を確認する。

時間分布はメインスレッドのCPU処理時間。`army_phase:*` は `daily:army_campaign` の内訳なので合計に二重加算しない。`search_estimated_bytes` はワーカー実行中の辞書を読まずに計算する保守的な容量見積りであり、実測の使用バイト数ではない。Godot全体のメモリ監視値を別に記録する。

当初方針の「距離×2は過大な下界」という記述は訂正した。同じ出陣元へ往復する場合は安全な下界である。進軍中は現在地→目標と目標→帰郡先を別に数え、実経路による帰郡費用も別途確認する。

## 確認方法

`python tools/verify_cpu_thinking.py` で時計、日次境界、探索、スケジューラ、CPU、35日間の全国進行、軍勢、自動命令、併合、制圧、外交、開始セッション、技術力命令を実行する。描画を伴う確認はWindowsのOpenGL実描画を使用する。ログと終了時のエンジン警告を `builds/qa/cpu-thinking-checks/` に残す。

実ウィンドウを最小化・復帰させ、日付停止・バックログ破棄・HUDの有限な寸法・実時間進行の再開も確認する。診断中の最小化で無効になったデータは採用せず、計測器はウィンドウ表示を固定し、中断時間を測定秒数から除外する。最小化でウィンドウ幅が0になってもHUDの倍率を0除算しない修正を加えた。

`tests/base_map/godot/benchmark_cpu_thinking.gd` は実時間で時計を動かす。新規ゲーム（山内上杉）を保存し、同じ状態へ毎回戻す。VSyncを無効にして30／60FPS、1・2・4・8倍を60秒×3回で比較する。戦争多発、AI選択停止、旧描画待ちの診断モードも備える。計測中に別のテスト・ビルドを動かさない。

```powershell
godot_console --path . --script tests/base_map/godot/benchmark_cpu_thinking.gd -- --seconds=60 --repeats=3 --fps=60,30 --speeds=8,4,2,1 --output=res://builds/qa/cpu_thinking_final.json
```

改修前の同条件8倍速（60秒×3回）の実進行は60FPSで2.50～2.53日／秒、30FPSで1.07～1.13日／秒だった（`builds/qa/cpu_thinking_baseline.json`）。ヘッドレスの手動時計テストの性能値とは比較しない。

## 実測とリリース確認

通常ケース：各60秒×3回、合計24回。すべて終了状態の現行形式セーブ検証に成功。Godot 4.7.2、Windows、OpenGL Compatibility、GeForce RTX 4060。FPSは上限値であり、実際のフレーム時間を別に記録した。

| 60 | 8 | 6.188 | 5.749～6.416 | 16.78 | 225.04 |
| 60 | 4 | 3.974 | 3.958～3.996 | 18.15 | 184.53 |

生データ：`builds/qa/cpu_thinking_final.json`。8倍速の平均は改修前に対し60FPSで約2.46倍、30FPSで約5.99倍の実進行量。ただし、**毎秒8日に到達したとはいえない**。必須日次処理、長く待つAIの締切、制圧時の更新が残る制限要因。CPU最大値には不可分な共通処理を含み、入力応答の6ms上限を保証するものではない。改修前のCPU最大値はリセット方法も異なるため、最大値の改善率は算出しない。

終了時の部隊数は0～57で、途中に出陣・帰郡・制圧が発生する。倍率ごとに進行した日数が違うため、終了時の部隊数だけで思考の品質を比較しない。低倍率で部隊が多い回は、進行速度を維持していても実描画がFPS上限を下回り得る。

12部隊を共通命令で出陣させ、資源を増やした診断配置から始める戦争多発ケースも、60秒×3回を両FPSで実行した。全6回の終了状態セーブ検証に成功。

| FPS上限 | 8倍速の実進行平均（日/秒） | 最小～最大 | フレームp95平均(ms) |
| --- | --- | --- | --- |
| 60 | 5.383 | 4.666～6.449 | 20.41 |
| 30 | 6.691 | 6.330～7.061 | 33.40 |

生データ：`builds/qa/cpu_thinking_war_final.json`。同じ論理状態に戻しているが、戦闘・忠誠イベントなどの乱数系列まで固定した再現性試験ではない。FPS間の勝率・戦略品質の比較には使わない。

原因分離用の診断は各FPSで60秒を1回ずつ実行。全4回の終了状態セーブ検証に成功。正式な3回反復の性能評価とは区別する。

| 診断 | 60FPS（日/秒） | 30FPS（日/秒） |
| --- | --- | --- |
| AI選択停止、必須日次更新は継続 | 7.998 | 7.996 |
| 旧仕様の固定描画待ちを再現、現行AIは有効 | 4.649 | 4.315 |

生データ：`builds/qa/cpu_thinking_no_ai_diagnostic.json` と `builds/qa/cpu_thinking_legacy_draw_diagnostic.json`。旧描画待ちの診断は改修前全体の再実行ではなく、時計の待ちだけを戻した比較。日次規則のみなら目標8日に近く、通常AIの締切待ちと戦時処理が残る制限要因だと判断した。

最終回帰確認は `python tools/verify_cpu_thinking.py` の14項目すべてで機能アサーションと終了コードが成功。途中探索の再要求に必要な判断・緊急度・元の予定日も保存し、読込後の状態一致を確認した。ゲームスクリプトの実行エラーは検出していない。時計のヘッドレス終了時にDummyMeshの解放診断、開始セッションの複数シーン切替終了時に4件のGLテクスチャ解放診断が残り、`builds/qa/cpu-thinking-checks/results.json` に記録している。

`python tools/export_windows_release.py` は終了コード0、書き出しログのエラー0件。2026年10月5日12:54（JST）の書き出し結果は `builds/windows-latest/export_report.json` にサイズ・SHA-256とともに保存。

生成した `builds/windows-latest/MyWorldsOnFreedom.exe` を実際に起動し、`-- --cpu-release-check` で35日進行、途中状態の保存・読込、CPU・外交状態の復元を確認した。結果は成功、失敗0件、CPU149家・6部隊・戦争1件、保存形式26。実行したEXEの絶対パスも記録している。生データ：`builds/qa/cpu_thinking_windows_release_result.json`。この起動確認は手動時計による機能試験であり、実時間の倍率評価には使わない。

Windows版は [EXE](../builds/windows-latest/MyWorldsOnFreedom.exe) と同じフォルダの [PCK](../builds/windows-latest/MyWorldsOnFreedom.pck) が成果物。

## 今回の実装範囲

既存ルールに沿う戦略・作戦情報・部隊命令の分離であり、GOAP／HTNへの全面移行ではない。集合地点は出陣元を使い、複数部隊の同時到着を待つ新しい命令や性格別重みは導入していない。兵力予約は目的地と兵糧の下界で到着可能性を確認する簡易方式で、将来の戦闘損失まで予測しない。

地域索引と海を隔てる連結領域の早期除外を採用し、地域上位グラフによる近似探索は採用していない。探索を別スレッドへ移した後の支配的負荷を計測してから、さらなる変更を判断する。PC性能やFPSに依存しない完全一致の行動系列、長期の勝率・目標振動・性格差については、今回の機能回帰と実時間計測だけで保証しない。

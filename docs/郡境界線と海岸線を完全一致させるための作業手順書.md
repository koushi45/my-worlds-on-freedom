# 郡境界線と海岸線を完全一致させるための作業手順書

作成日：2026-09-19  
状態：実施前。現行コードを確認して作成した手順書であり、地形・郡形状の修正はまだ行っていない。

## 1. 目的と完了条件

本土の沿岸郡について、海に接する外周をベース地図と共通の海岸線から再構成する。国境表示で使用している海岸線参照方式を手本とし、郡の白線、テーマカラーの内側フェード、領地塗り、選択時の点滅、クリック判定を同じ確定形状に統一する。

「完全一致」は、海岸線に近づけることではなく、同じ海岸線IDと同じ区間を参照することを意味する。海岸線の途中に郡境の接続点がある場合は、同じ線分上の点として一度だけ計算し、両隣の郡で共有する。独立した近似線や目視による描き直しは使用しない。

完了には次のすべてが必要。

- 対象の海岸区間に欠落・二重割当・湾を横切る直線・海上への領地はみ出しがない。
- ベース地図の陸地側に沿岸郡の未割当帯が残らない。
- 隣接郡どうしの隙間・重なりがなく、郡境と海岸の接続点が共有される。
- 白線だけでなく、塗り・内側フェード・選択表示・クリック領域も一致する。
- 国境、陸地マスター、既存の支配家・支配者、郡ID、島の採用方針を意図せず変えない。
- 数値検証、全沿岸区間の画像確認、更新したWindows実アプリでの確認が完了している。

線の太さやアンチエイリアスによる海側への半線幅の表示は、線の中心位置がずれる問題と分けて判定する。ラスタ画像の画素端とベクトルの中心線が画素単位で同一になることを保証するものではない。低解像度画像や標高投影に由来する見かけの差は別途検証する。

現在の `test_independent_districts.py` は国境を越える郡形状の維持を検査している。**郡を所属国ポリゴンで切り抜く修正は行わない。** 修正する外周の基準は国境ではなく、共通の陸地・海岸線とする。

## 3. 作業前の保存と対象確定

1. 作業ツリーの変更を確認し、既存の作業を保存する。Git未追跡ファイルも含め、変更対象の生成元・生成物・直前のEXE/PCKを復元可能な場所へ退避する。
2. 陸地マスター、共通海岸線、承認済み国境、郡形状、統治データ、生成ツールのSHA-256を記録する。
3. 添付画像と同じ場所をアプリで再現し、郡ID・郡名・カメラ位置・ズーム・標高表示状態・ウィンドウ解像度を記録する。郡名コピー機能を利用してよい。
4. 全郡について、本土陸地から外へ出た面積、陸地上の隙間、海岸線との距離、重複面積を集計する。全周の距離を使うと内陸境まで誤検出するため、沿岸外周と内陸共有境界を区別する。
5. 本州・九州・四国・北海道と、対馬・平戸島・村上水軍領地・淡路島を対象にする。それ以外の離島に郡を復活させない。面積順位だけで本土・島を判定せず、海岸線IDと既存島台帳を照合する。
6. 初期の検証資料を `data/work/districts/coast_alignment/` に保存する。このディレクトリは本手順で新規作成する作業用領域とする。

## 4. 共通海岸線と沿岸区間の台帳を作る

1. 陸地マスターから派生したゲーム座標系の点列を読み、ベース画像と承認済み国境が同じマスター・座標変換を使っていることを確認する。異なる場合は、先にその不一致を報告・解消する。
2. 海岸線をID別の閉じたリングとして扱う。内水面や穴の扱いを海岸と混同しない。国境線に含まれる行政境界を陸地外周の代わりにしない。
3. 国境の既存方式にならい、各郡の沿岸外周を次の情報で記録する。

   - `district_id`、`coastline_id`、区間ID
   - `start_distance`、`end_distance`、`wrap`、進行方向
   - 両端の共有接続点ID
   - 参照元のハッシュ、判定根拠、要確認状態

4. 元のリングの全中間頂点を保存し、区間内の湾・岬・入り江を省略しない。リング終点をまたぐ区間も復元できるようにする。
5. 郡境が海岸へ着地する点を、隣接郡で一つの共有ノードとして登録する。接続線の交点または確認済み沿岸到達点を、対応する海岸線分上に配置する。
6. 最近傍点だけで狭い湾の対岸へ接続しない。候補が複数ある場合は元の境界方向、沿岸区間の順序、隣接郡、同じ陸地成分への所属を照合し、解消できない箇所を要確認一覧へ残す。

## 5. 郡形状を共通海岸線から再構成する

1. 内陸共有境界と沿岸区間を分離する。内陸の形状と国境を越える既存の郡は維持する。
2. 沿岸に接続する内陸境の終端だけを共有接続点へ接続し、接続点までの変更範囲を記録する。内陸全体の平滑化は行わない。
3. 共通海岸区間と内陸共有境界を結合し、交点で分割した一つの境界ネットワークから閉じた面を生成する。
4. 面の所属は既存の郡ID、内部の代表点、元の郡との重なり、隣接関係を用いて決める。複数候補が残る面や広い未割当面を単純な最近傍で強制配分しない。
5. 海へはみ出す面を取り除くと同時に、元の郡外周が内陸へ引っ込んでいた区間を共通海岸線まで補う。`郡 ∩ 陸地` の切り抜きだけでは後者の隙間を埋められないため、それだけで完了にしない。
6. 全郡の海岸側の外周を、登録した共通区間の点列から復元する。海岸側へ `simplify`、丸め、独立したスナップを再適用しない。
7. 幾何修復で形状が変更された場合は面積差・部品数・境界差を再検証する。`make_valid` やバッファ処理の成功だけを正常の根拠としない。
8. 郡ID・名前・支配家・支配者を保持する。ラベル位置が郡外になった場合だけ、郡内の代表点へ更新する。家紋位置もその点を使う。
9. 最終形状から拠点の包含候補・境界接触・隣接関係を再計算する。形状変更に伴う候補変更と領有変更を混同しない。

独立郡の生成パイプラインには、飛び地・重複整理後に沿岸再構成を追加する。島の確定形状を適用した後、最終形状で包含・接続性を更新する。以後に旧形状へ戻す整理処理を走らせない。`curate_island_districts.py` 内の拠点候補再計算もこの順序と整合させる。

作業用の修正結果のみを手で上書きする運用にはしない。再生成しても同じ結果になるよう、区間参照台帳と生成処理へ修正を記録する。

## 6. 白線・塗り・フェード・クリック判定を統一する

1. 郡白線は確定したポリゴンと共有海岸区間を使う。海岸上へ旧比較形状の白線を重ねない。
2. 領地塗りと選択時の点滅用メッシュを確定形状から再生成する。海上に塗りが残っていないことを確認する。
3. フェードも確定形状から生成する。既存の「内側距離帯を重ならない面へ分割する」方式を維持し、海側への色漏れ・途中の色変化・断線・重なりによる濃化を再検証する。
4. クリック判定、空間検索用bounds、ラベル、家紋の座標を更新する。描画だけ変更して旧クリック領域を残さない。
5. 標高あり／なしの双方で、海岸線・郡白線・メッシュ外縁へ同じ座標変換を使う。長い線分の細分化点が異なると投影後の輪郭がずれるため、共通頂点と同じ投影サンプリング規則を使う。
6. 採用離島の `coastline_only` は維持し、島専用の郡境線を追加しない。
7. ズーム200%ちょうどは既存実装どおり国表示、200%を超えると郡表示とする。切替によって海岸側の輪郭が飛ばないことを確認する。

## 8. 数値検証

新設予定の `tools/verify_district_coast_alignment.py` で、実行時に採用される全郡を検証する。これは現時点で存在するコマンドではなく、実装時に追加する検証器である。

| 検査 | 合格条件 |
| --- | --- |
| 共通海岸の参照 | 全沿岸区間に海岸線ID・距離区間があり、参照元ハッシュが一致 |
| 区間の連続性 | 対象海岸リングの割当区間に欠落・重複がない |
| 海岸上の頂点 | 元線分上の分割点を除き、参照した元の頂点列を保持 |
| 海上へのはみ出し | 各郡と対象陸地との差分面積が数値誤差内 |
| 沿岸の未割当帯 | 対象陸地と郡集合の和集合との差分を集計し、沿岸部の未解決がゼロ |
| 隣接郡 | 内部面積の重なりがゼロ、共有境界と接続点が一致 |
| 有効性 | 全ポリゴンが閉じていて有効、自己交差・空形状がない |
| 再現性 | 同じ入力から2回生成して同じ内容・ハッシュになる |
| ゲーム情報 | 既存の郡ID・所有者・支配者・島採用方針を維持 |
| 派生メッシュ | 三角形の和集合と確定形状／フェード帯の差が数値誤差内 |

幾何計算の許容誤差はゲーム座標の倍精度演算用と、実行時float32用を区別し、検証レポートへ明記する。許容誤差をずれを隠すために緩めない。目安として面積誤差は既存メッシュ検証の `max(1e-5, 面積×1e-9)` を参照し、海岸区間の一致は距離の許容値だけでなく参照ID・頂点列でも判定する。

既存の回帰検査も実行する。

```powershell
python -m unittest tests.base_map.test_independent_districts tests.base_map.test_independent_fill_meshes tests.base_map.test_district_enclaves tests.base_map.test_provisional_overlaps
godot_console --path . --script res://tests/base_map/godot/test_independent_districts.gd
godot_console --path . --script res://tests/base_map/godot/test_kamon_render.gd
godot_console --path . --script res://tests/base_map/godot/test_enclave_saves.gd
godot_console --path . --script res://tests/base_map/godot/test_governance.gd
```

国境を越える郡や島の制約を満たすためにテストを削除しない。形状の正当な変更で件数などの固定期待値が変わる場合は、差分の理由を記録して更新する。既存テストの成功だけでは共通海岸の完全一致を保証しないため、新設の全区間検証を必須とする。

## 9. 実画面確認

1. 最初にユーザー添付画像の再現地点を修正前後で同条件撮影する。
2. すべての沿岸郡を対象に、海岸区間が端から端まで写る連続した画像を保存する。一つの代表点の撮影だけで済ませない。狭い湾、細長い半島、河口、郡境の着地点を重点確認する。
3. 拡大率50%・200%・201%・300%・400%、標高あり／なしを確認する。国表示側も海岸位置の比較用に記録する。
4. 白線だけ、フェードあり、領地塗りあり、選択点滅ありの状態を確認する。フェードの欠けや別家の色の混入がないことを確認する。
5. 海岸の陸側・海側、郡境の両側をクリックし、見えている領域と判定が一致することを確認する。既存の境界付近の選択許容範囲は記録し、遠い海上まで郡が選べる状態にしない。
6. 左ウィンドウの郡名・支配者名、郡名コピー、家紋位置も確認する。
7. ウィンドウサイズ1280×720・1920×1080・3840×2160で、同じ地理的区間のずれ・線幅・欠落を比較する。
8. 全画像を「郡ID／海岸区間ID／撮影条件／合否」の一覧へ紐付ける。未撮影・未確認区間が残る状態で全郡確認済みと記載しない。

## 10. Windows版の出力と確認

数値検証・画面確認の合格後、更新した郡データと全派生メッシュを含めて書き出す。

```powershell
godot_console --headless --path . --export-release "Windows" "builds/windows-latest/MyWorldsOnFreedom.exe"
```

出力ログのスクリプトエラー・リソース不足を確認し、EXEとPCKの更新日時・SHA-256を記録する。更新したEXEを起動して新規ゲームと既存セーブの双方で再現地点を確認する。終了コード0は起動確認にすぎず、沿岸一致の検証の代わりにはしない。

配布はEXEとPCKを同じ世代の組で扱う。不具合時は記録した直前版の組と対応データへ戻せるようにする。既存セーブを削除して検証を通す運用はしない。

## 11. 作業完了時に残すもの

- 修正した生成処理と、再生成可能な海岸区間参照台帳。
- 入力ハッシュ・変更郡一覧・面積差・海岸区間の割当・未解決件数を含む検証レポート。
- 全沿岸郡の画像一覧と、添付画像地点の修正前後比較。
- 郡ID・統治情報・国境・陸地マスターが維持されたことの差分記録。
- テスト結果、Windowsビルドログ、EXE/PCKのハッシュ。

完了報告は「確認した全沿岸区間数」「未確認／未解決区間数」「検証した表示条件」を明記する。未解決区間がある場合は対象IDと理由を示し、完全一致が完了したとは報告しない。

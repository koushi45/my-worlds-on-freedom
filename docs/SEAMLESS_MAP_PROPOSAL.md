# シームレスな地図操作・スマホ向け並列処理の改善案

2026-09-13。コード調査に基づく設計案。以下の新方式は未実装で、数値は実機検証前の初期目標。

追記：この設計に基づく実装を追加した。[実装内容・検証・実機での残件](SEAMLESS_MAP_IMPLEMENTATION.md)を参照。以下は当初の設計記録として残す。

## 方針

操作中は常に地図を描く。カメラの移動・拡大縮小は準備済みの描画データだけで進み、読み込みやCPUジョブの完了を待たない。近隣と次の倍率のデータを容量の範囲内で先読みする。準備が間に合わない場合は低精細の地図を描き続け、詳細だけを後から更新する。

CPU負荷の大きな計算は複数ワーカーで処理する。障害はジョブ単位のログと再現テストで原因を特定し、並列処理を維持して修正する。

## 現状で確認した問題

|箇所|確認できた実装|影響|
|`main_map.gd::set_map_zoom` / `_clear_loaded_tiles`|LOD変更時に表示タイルと補完用の全国図を破棄|次の表示準備より先に現在の表示を失う。白抜けの全原因を実描画で確定したわけではないが、表示が途切れ得る経路がある|
|`_refresh_visible_tiles`|表示範囲を2座標単位だけ拡張して検索。不要タイルは即時破棄|近隣の先読み範囲として不十分。往復操作でも再取得しやすい|
|`map_asset_stream.gd`|非同期読み込みは最大2件。表示要求にない待機要求は削除|実用的な先読み優先度・保持期間がない。CPU加工の並列化とは別の仕組み|
|`district_layer.gd::load_parent`|読み込み後に国単位のデータを深いコピーし、線の空間索引を組み立てる|I/Oが非同期でもメインスレッドに大きなCPU処理が残る|
|`district_layer.gd::_draw` / `line_mesh_batch.gd`|倍率に応じた破線の分割と頂点・索引生成|ズームのたびに線のデータが変わり、CPU加工・GPU登録が発生する|
|資産メモリ管理|Android保持キャッシュ96MiB。通常タイルの見積もりは1件64MiBで固定|1件で予算の約2/3を占める計算。実際の圧縮形式・共有資産・表示中の参照・作業領域を表さず、追い出しと再取得を招き得る|
|`map_diagnostics.gd`|共有ロック中にJSON化・書き込み・flush|監視スレッドはあるが、ログ呼び出し元や状態更新がディスク処理を待ち得る|

前回の432回テストは「処理が停止せず完了した」確認であり、「全フレームに地図が描かれた」「スマホで滑らかに動いた」という合格判定ではない。白抜けと操作遅延を別の品質要件として測る。

## 1. 常駐する低精細地図と、準備後の差し替え

- 起動時に軽量な全国地図を読み込み、最初の描画完了後に操作を有効にする。初回準備は起動画面で進捗を示す。
- 全国地図は操作中に破棄しない。キャッシュの追い出し対象から外し、地形・海・最低限の海岸線を常に覆う。現在の大きいLOD0資産をそのまま常駐させるだけでなく、軽い専用テクスチャと粗いメッシュを生成する。
- タイルは `要求 → 読込中 → CPU準備済み → GPU登録済み → 表示中 → 保持 → 解放` の状態で管理する。読み込み完了と描画可能を区別する。
- 新タイルが描画可能になるまで、対応する領域の旧タイルを残す。新旧切り替えは領域単位で行い、一括クリアを廃止する。
- 画面外の領域へ急に移動しても全国地図で覆う。未準備の詳細だけが一時的に粗くなる。
- 平面／立体切り替えも次の投影の全国図が描画可能になるまで現在の投影を維持する。カメラ・拠点・境界を同じ投影世代で切り替え、位置がずれる中間フレームを作らない。
- 全画面のクロスフェードは必須にしない。まず描画の被覆を保証し、スマホの重ね描きとメモリ増加を抑える。

**仕様変更：詳細の表示には遅延を許すが、地図の表示と操作には読み込み待ちを入れない。**

## 2. 近隣と次の倍率の先読み

- 現在の表示範囲、周囲1タイル分、移動方向の前方を候補にする。すべてを無条件に確保せず、バイト予算まで優先度順に読み込む。
- 移動速度と実測の読み込み時間から必要距離を調整する。初期値は前方0.3〜0.5秒分を想定し、速い移動でも上限を設ける。
- 次のLODへ近づいたら、拡大方向または縮小方向の隣接LODを先読みする。全倍率の詳細を常駐させない。
- 優先順位は「現在の表示に不足する詳細 → 切り替え直前のLOD → 移動先 → 周囲 → 最近離れた領域」。古い低優先度ジョブは開始前に外す。
- 一度表示した近隣は短期間保持する。初期値は2〜3秒だが、容量に余裕がなければ早く解放する。表示中・切り替え中・常駐分は保護する。
- 操作イベントごとに新規ロードを発行しない。必要タイル集合、予測領域、LODが変わったときだけ差分を要求する。同じ資産の要求を重複させない。
- 静止して必要範囲が揃ったら、読み込みとCPUジョブを止める。

**仕様変更：カメラの倍率は連続、内部の精細度は段階的に更新する。** 境界付近の往復でLODが反転しないよう、拡大側と縮小側の切り替えしきい値に10〜15%程度の幅を設ける。

## 3. 重いCPU計算を複数ワーカーへ分散

|実行場所|担当|
|ビルド時|地形のLOD、平面／立体の形状、空間索引、境界の累積距離、描画用の分割データを事前生成|
|非同期読み込み|優先度と容量予約に基づく資産取得。同じパスは1要求に統合|
|CPUワーカープール|必要なデータ展開、検証、幾何加工、空間検索、ラベル配置候補、選択判定。タイルや空間チャンク単位で分散|
|メインスレッド|入力、カメラ更新、完成済み結果の取得、シーンへの反映。未完了ジョブを待たない|
|GPU|既存メッシュの描画、線幅、破線の見え方の調整|
|ログ専用スレッド|通常ログの整形・出力・ローテーション|
|独立監視スレッド|メインスレッドとジョブの進捗停止を検出。CPUワーカープールの空きを待たない|

Godotの `WorkerThreadPool` を使い、ジョブは読み取り専用入力と専有する出力バッファを持つ。複数ワーカーで同じResource・Dictionary・描画ノードを書き換えない。完成結果の受け渡しだけ短いロックで保護する。

ジョブにはタイルID、データ版、投影モード、要求世代を付ける。完了時に最新の表示要求と合わなければ画面へ反映しない。同一データ版で再利用可能ならキャッシュへ戻す。協調キャンセルと例外・失敗時の資源回収を設け、完了済みタスクは回収APIで確実に解放する。

実行中のシーンツリーやGPUへの直接操作にはGodotの制約がある。その最終反映だけをメインスレッドに残す。これはCPU計算をシングルコア化する方針ではない。[Godotのスレッド安全性](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)、[WorkerThreadPool](https://docs.godotengine.org/en/stable/classes/class_workerthreadpool.html)。

CPUジョブの同時実行数はスマホでまず2、余力のある端末で3〜4を検証する。OSが物理コアへの割り当てを行うため、スレッド数とコア数を同一視しない。全コア100%を目標にせず、メインスレッドの処理時間、発熱、消費電力、フレーム時間を見て調整する。小さな計算のスレッド化は逆効果になり得るため、重い単位にまとめる。[WorkerThreadPoolの注意事項](https://docs.godotengine.org/en/stable/classes/class_workerthreadpool.html)。

## 4. 毎回のCPU処理自体を減らす

- 郡境の破線は、累積距離付きの線メッシュを事前生成し、シェーダーで表示区間を決める。倍率変更はパラメーター更新だけにする。境界の接合部で位相を合わせる。
- 国別の大きなデータを描画用の空間チャンクへ分割する。史料上の国・郡IDと選択の正本は保持し、表示処理の単位だけを変える。
- 地形・国境・河川・海岸線も表示倍率に合う描画データを使う。遠景で詳細形状をすべて加工・描画しない。
- ラベルは操作中に直前の配置を使い、重い重なり判定は更新頻度を下げる。操作が約100〜150ms落ち着いたら詳細配置を更新する。重要な拠点・選択対象は維持する。
- 読み込み失敗・版不一致時に、メインスレッドで巨大なJSON解析や形状生成を始める経路を廃止する。現在の地図を保持してログを記録し、必要な復旧はバックグラウンドの独立ジョブで行う。
- GPU登録は初期予算1〜2ms/フレームで分割する。単一の登録処理が予算を超える場合は、その資産を小分けに再生成する。ループの時間制限だけでは単発処理の停止を防げない。

## 5. スマホのメモリ管理

単なるキャッシュ容量に加え、常駐地図、表示中資産、切り替え中の旧新資産、先読み、展開途中のCPUデータ、完了結果キュー、GPU転送中の領域を予算に含める。

- テクスチャの実フォーマット・mipmap、頂点・索引配列、共有資産を考慮する。共有分を二重計上せず、表示ノードが保持する分も追跡する。
- 各ジョブの開始前に入力・展開後・出力の最大作業領域を予約する。完了結果をメインスレッドが取り込む前に次々に積まない。
- 現在の96MiBを「総使用メモリ」と扱わない。AndroidのPSS等、プロセス全体の値を実機で測定する。
- 初期検証では地図関連資産128MiB程度の管理予算と、プロセス全体PSS 300MiB以下を仮目標にする。両者は別の計測値であり、単純加算しない。対象端末・他画面の必要量に応じて見直す。
- メモリが厳しい場合は、先読み範囲、保持期間、高精細データから順に縮小する。全国地図と表示被覆は維持する。
- スマホ標準は30fps、対応端末で60fpsを選択可能にする。400%の操作倍率は維持できても、低メモリ設定では最高精細度を下げる仕様を許容する。

## 6. 並列設計を維持した診断・不具合修正

現行の監視機能を拡張し、エラーだけでなく遅延と表示欠落も記録する。ログ呼び出し元は容量制限付きキューへ小さなイベントを追加して返り、JSON化と通常のディスク出力は専用スレッドへ移す。ファイルI/Oを状態共有ロックの中で行わない。重要イベント用の予約枠と、通常ログを間引いた件数も記録する。

イベントの共通項目はセッションID、ジョブID、タイルID、入力版、要求世代、スレッドID、単調時刻、処理段階、キュー待ち・CPU処理・ロック待ち・GPU反映の時間、メモリ予約量、失敗理由とする。障害時は直前の操作・ジョブ履歴を容量制限付きリングバッファから保存する。

表示欠落は画面の白色の数だけで判定しない。海やUIも含むため、地図が描くべき領域の被覆状態と実描画の両方で判定する。低精細による補完、切り替え回数、キャッシュヒット率、キャンセル、読み込み再試行を測る。

修正の手順は「ログで工程・入力・待ち先を絞る → 同じ条件を並列実行で再現 → 所有権違反・ロック競合・無限ループ・重複要求等の直接原因を修正 → 順序を入れ替えた回帰テスト」。単一ワーカー化や同期ロード化を恒久対策にしない。前回の破線停止は浮動小数点端数で処理が進まない問題であり、並列処理の競合が確認された障害ではない。

## 7. 合格条件と実装順

数値は対象スマホ選定後に確定する。PCのRTX 4060の測定だけでスマホ合格にはしない。

|検査|初期の合格条件|
|表示継続|全国〜400%の往復、連続移動、平面／立体切り替えで、起動完了後の地図被覆欠落0フレーム|
|低速読み込み・失敗|読み込みに500msの遅延、資産失敗、キャッシュ枯渇を注入しても全国図と操作を維持|
|フレーム|標準30fpsでフレーム間隔p95 33.3ms以下、p99 50ms以下、操作中100ms超の停止0を目標|
|単一スレッドの負荷|地図由来のメインスレッドCPU処理p95 4ms以下を初期目標。GPU待ち・入力から描画までの遅延も別計測|
|先読み|同じ領域・倍率を往復する定型経路で準備済みデータの利用率を測定。冷えたキャッシュでも表示継続|
|メモリ・発熱|低〜中位スマホで30分往復し、PSS・GPU資産・各スレッドCPU時間・温度傾向を確認。キャッシュが温まった後に増え続けない|
|並列の正しさ|完了順序の入れ替え、キャンセル、連打、バックグラウンド移行・復帰で古い世代の誤反映とデータ破損0|
|ログ|各障害注入で入力と失敗工程を追跡でき、ログ出力の遅延が操作待ちに波及しない|

実装は以下の順序を推奨する。各段階で上の表示継続検査を行う。

1. **常駐全国図・旧表示保持・描画可能になってからの差し替え**。表示欠落の自動検査と工程別計測を加える。
2. **資産の分割・正しい容量管理・先読み・LOD切り替えの往復抑制**。読み込みと保持の無駄を減らす。
3. **CPUワーカー分散・郡境シェーダー化・索引の事前生成・非同期ログ**。計算量とメインスレッド負荷を下げる。
4. **スマホ実機での調整と障害注入**。端末別の並列度、先読み量、解像度、フレーム上限を確定する。

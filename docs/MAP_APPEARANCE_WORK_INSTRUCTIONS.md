# 創造PKの画面を参考にした地図描画の作業手順書

作成日：2026年9月30日。対象：My Worlds on Freedom の地図描画。

拡大に応じて南側から見下ろす視点へ変える設計と実装順序は、[倍率と視点角度の手順書](MAP_ZOOM_VIEW_ANGLE_WORK_INSTRUCTIONS.md) を参照する。以下の実施結果は固定投影での配色・質感の改善であり、可変角度の実装結果とは区別する。

目標は、起動中の「信長の野望・創造 with パワーアップキット」で観察した、明るい平野、細かな植生の色むら、形がよく読める山地、落ち着いた水面を、本作の地形データから作ること。まず既存の2D地形投影を使い、色と照明の改善を小地域で比較してから全国へ展開する。

本書は作業手順と判断基準をまとめたもの。手順中の調整値は試作の開始値であり、参考ゲームの設定値や解析結果ではない。2026年9月30日にこの手順に沿って描画を改善した。採用値と確認結果は末尾に記録する。

## 参考画面で確認した見た目

2026年9月30日にユーザーが起動したゲームを、ホイールで拡大・縮小して観察した。近景の平野、山地を含む中景、海岸と海が見える広域表示を比較し、ズーム直後の動きが落ち着いた画面も確認した。観察範囲は表示中の地域・日時・画面設定に限る。他季節、夜間、全国の地形を確認したものではない。

| 対象 | 画面で確認できた特徴 | 本作で目指す見た目 |
| --- | --- | --- |
| 平野 | 黄緑・草色・深緑の色むらが連続し、細部が面としてまとまる | 平野の明るさを保ち、大小の色むらを自然につなぐ |
| 森林 | 暗い緑のまとまりに細かな濃淡があり、斜面に沿って広がる | 丸い木の記号を並べず、植生の密度と斜面の陰影で森林を表す |
| 山地 | 稜線の明るい面と谷の暗い面がはっきり分かれ、尾根が連続する | 実標高に沿った面の向きと陰影で地形を読ませる |
| 岩肌 | 山の上部や急斜面に淡い黄灰色の面が見える | 急斜面の一部に岩色を混ぜ、割れ目の線を描かない |
| 水 | 海は暗い青灰色に細かな波があり、川は地表から読める青色 | 陸地と調和する水色と、控えめな水面の変化を作る |
| 道路 | 土色の細い線が平野と谷を通り、地表から浮かずに読める | 本作の既存道路を、地形に馴染む色と線幅へ調整する |
| 空気感 | 広域の上方ほど青灰色を帯び、白い雲が疎らに見える | 地表の完成後に、弱い遠景の霞を試す |
| 政治境界 | 発光する赤系の境界が地表と明確に分かれる | 本作の家色・境界の読みやすさを保ち、光り方を抑制する |

画面だけでは、参考ゲームのメッシュ密度、テクスチャ解像度、樹木のモデル構成、陰影の計算方法は特定できない。以下は観察した見た目を作るための、本作向けの設計案である。

## 参考にする範囲

参考にするのは配色、明暗の階層、質感の粒度、地形の見え方、地表と線のバランス。地形、河川、海岸、道路、国郡境界、史跡、ゲームの仕組みは本作の既存データと方針を使う。参考ゲームの画像・モデル・地形データを資産として取り込まない。

直前に削除した森林の丸い樹冠、草原の独立した斑点、岩場の割れ目は再導入しない。細かな質感は、境界を持つ記号ではなく連続する弱い色・明暗の変化で作る。

道路は六角形レイヤーの子として隣接する六角形の中央を結び、200%以上で表示する。城・港のマップ記号と名称は追加しない。郡奉行所の家紋・家色、六角形、等高線の開発者表示などの既存方針を維持する。参考画面に見えた城下町、家屋、航路は今回の対象に含めない。

## 現在の描画と改善する順序

| 現在の仕組み | 確認した実装 | 改善時の扱い |
| --- | --- | --- |
| 地図座標 | 承認済み陸地と8192×8192座標 | 維持する |
| 起伏の投影 | `elevation_surface.gd` の16座標単位の三角形格子、固定の傾斜と斜交 | 最初の色・照明試作では維持する |
| 地表画像 | `terrain_texture.py` が実標高と世界座標の連続ノイズから生成 | 色画像と照明を分離する試作を作る |
| 照明 | 色画像の焼き込み陰影に、全国の `terrain_lighting.png` の補正を乗算 | 二重の陰影を避け、高精細な斜面照明と広域の影を役割分担する |
| 近接画像 | 211地域、通常1032px・近接1548px・高倍率2064pxの正方形PNG | 原寸の各段階を事前生成する |
| 倍率 | 最大800%、250%以上で近接画像、400%以上で高倍率画像 | 維持する |
| 読み込み | 可視地域をストリーミング。PCの地図管理予算320MiB | 全地域の一括常駐を避け、試作前後で実メモリも測る |

改善順は、照明の整理 → 平野と森林の色 → 地形に沿う細部 → 水と線の調和 → 霞 → 必要に応じた表示メッシュの改善とする。最初から全部を変更すると、どの変更が効いたか比較できなくなる。

現在の16単位の格子は800%の平面表示では格子間隔が約128画面ピクセルになる。これは画像解像度とは別の問題で、画像を細かくしても山の輪郭・変位の細かさは増えない。また全国照明画像は4096pxなので、800%では照明の1画素が平面表示で約16画面ピクセルに相当する。細かな山肌の照明を全国画像だけに任せない。

## 手順1 比較用の小地域を決める

1. 平野と山地と河川を含む地域、森林主体の地域、海岸の地域を各1か所選ぶ。最初の作業は1地域と隣接タイルだけに限定する。
2. 復元済みの現在画像を基準として保存する。元PNG、生成設定、使用DEM、ハッシュを記録し、比較用の派生資産は試作ディレクトリへ出す。
3. 同じ地図座標・画面サイズ・カメラ・倍率で、平面と立体の画像を保存する。基本比較は200%・400%・600%・800%とする。
4. 初めは霞・雲・境界を隠した地表だけを比較し、その後通常の六角形・道路・家紋・境界を重ねる。地表だけが美しくても、通常画面で情報が読みにくければ採用しない。

記録する比較案は A 現在、B 照明だけ変更、C 色も変更、D 弱い細部も変更の4案とする。採用理由を画面の違いとともに残す。

## 手順2 地表色と照明を分ける

### 細かな斜面と広域の影を分担する

`tools/terrain_texture.py` に、照明を含まない地表色を生成する試作モードを追加する。既存の `colour *= shade` を外すときは、必ず同じ試作で照明側も置き換える。現在の `build_terrain_relief.py` は焼き込み陰影を補正するために `illumination / original` を使っており、色画像だけを変更すると明暗が不整合になる。

高倍率タイルの描画用DEMから細かな斜面の向きを求め、その解像度で拡散光を計算する。全国DEMでは広い谷の遮蔽と大きな山の影を作る。小さな陰影と広域の影を同じ強さで重複させない。

試作の概念式は次の通り。法線は斜面の向きを表すベクトルで、光の向きも同じ座標系へ揃える。

```text
N = normalize(-height_dx × relief_strength,
              -height_dy × relief_strength, 1)
diffuse = max(dot(N, light_direction), 0)
illumination = ambient + diffuse_strength × diffuse
illumination *= (1 - shadow_strength × broad_shadow)
illumination *= (1 - occlusion_strength × valley_occlusion)
ground = albedo × illumination
```

試作開始値は `ambient=0.55`、`diffuse_strength=0.45`、`shadow_strength=0.15`、`occlusion_strength=0.08`。光は画面の左上側からに統一し、現行の北西の光を出発点にする。明るい面は黄緑、暗い面は青緑を少量混ぜて、影の中にも地表色を残す。値は調整用の提案であり、参考画面から計測したものではない。

表示メッシュの高さ、細部用の描画DEM、照明の起伏強調量は一致しない場合がある。主稜線が見た目の山の形とずれたら、先に表示高さへ対応する広域の照明を合わせ、その上に弱い細部の照明を足す。照明だけで存在しない主峰を作らない。

色への光の乗算は、試作では地表色をsRGBから線形色へ変換して行い、PNGへ保存するときにsRGBへ戻す。実行時合成へ移す場合も、画像とシェーダーの色変換を確認して二重変換を避ける。色空間を変えた案は従来の乗算と明るさが変わるため、係数を流用せず比較し直す。

斜度計算と平滑化には出力範囲より広いDEMを渡し、計算後にタイルを切り出す。余白は使うフィルターの半径を満たす長さにする。長距離の影は全国または十分広い範囲で求め、各タイル内で影の計算を打ち切らない。

### 実装方式を小地域で選ぶ

固定の光を使う最初の試作では、高精細な照明を生成時に計算し、最終色を各PNGへ焼き込む方式が最も変更範囲を絞りやすい。この場合、現行シェーダーの全国照明乗算を試作タイルでは中立にし、影を二重に掛けない。色と照明は生成工程と調整用出力では分けて保持する。

実行中に光を調整する必要が生じた場合は、地表色と照明画像を別に読み込む方式を比較する。これは追加画像のGPUメモリを測ってから採用する。現在の `terrain_relief.gdshader` は `canvas_item` と `unshaded` を使うため、3Dの光や影を追加しただけでは照明は適用されない。使うならフラグメント処理で照明を明示的に合成する。[Godot CanvasItem shaders](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/canvas_item_shader.html)

完了条件は、主稜線・谷の方向を保ち、日陰でも森林の緑が読め、平野が白く飛ばず、隣接タイルで照明の段差がないこと。

## 手順3 平野と森林を連続する色で作る

平野は明るい草色を基調に、黄土色と低彩度の緑を混ぜる。森林は平野より暗く、少し青寄りの緑を使う。地形区分の境目を硬い塗り分けにせず、標高・斜度・周囲の広い色分布で徐々に移り変わらせる。

独立した点や丸を描く処理は入れない。細部は連続した濃淡の帯を重ね、各模様の中心や外周が木・斑点として見えないようにする。森林と草地の違いは、平均色、密度のまとまり、濃淡の細かさで出す。

| 層 | 試作で使う世界座標の長さ | 役割 | 調整の目安 |
| --- | --- | --- | --- |
| 大きな分布 | 32〜96座標単位 | 明るい平野と暗い植生のまとまり | 最初に決める。地形区分を全部ノイズで決めない |
| 中くらいの分布 | 4〜16座標単位 | 植生密度と地表色の変化 | 大きな分布を補い、雲状のむらを強くしすぎない |
| 小さな濃淡 | 0.25〜1座標単位 | 草や森林を感じる連続した表面変化 | RGBで±2〜5程度から試し、孤立した点を作らない |

長さと濃淡は提案値。800%では0.25〜1単位が平面表示で約2〜8画面ピクセルになる。細部は世界座標へ固定し、倍率変更で模様が移動・再抽選されないようにする。小さな模様が800%で丸や粒に見えたら、濃淡を下げ、分布を連続化する。

岩色は標高だけで一律に付けず、急斜面の一部へ薄く混ぜる。尾根の明るさは実標高由来の照明で出す。割れ目、黒い縁、稜線をなぞる白線を追加しない。雪は現行の高山表現を基本とし、観察していない季節の雪線を参考ゲームの仕様として推定しない。

完了条件は、森林が面のまとまりに見え、草地が細かな点描に見えず、岩色を消しても山の形が照明で読めること。

## 手順4 画像の解像度と補間を整える

通常・近接・高倍率を同じ世界座標、同じ色と光の設定から生成する。現行の1032・1548・2064pxと、1座標単位の周辺余白を維持する。主地形や植生の位置を解像度ごとに変えない。

最初は各段階を個別生成して現行方式と比較する。細部が解像度の切り替えで跳ねる場合は、同じ高解像度の作業画像を制作時に縮小する方式を比較する。実行時はその倍率用の完成済み画像を読む。縮小した画像で陰影や色が変わらないか確認してから採用する。

補間は線形を基本にする。最近傍は丸や粒の代わりに画素の四角さを目立たせるので、ぼやけ対策の主手段にしない。縮小時に細部がちらつく場合だけ、ミップマップと対応するフィルターを試す。現行の詳細PNGではミップ生成が無効なため、導入時は取り込み設定とメモリ計上を両方更新する。

2064×2064のRGBA8画像は非圧縮で約16.25MiB。ミップ全段を持つ場合の目安は約21.7MiBで、別の照明画像も加えると負荷が増える。これは画素データのみの概算であり、実際のGPU形式・ドライバー・管理オブジェクトの確保量とは分けて測る。320MiBの地図管理予算内で、表示中と読み込み待ちの資産を保護し、画面外の不要資産を解放する。

全国を1枚の巨大テクスチャへ統合しない。Godotの公式資料もデバイスごとのテクスチャ寸法制限と、モバイルでの大きな画像の制約を説明している。本作では既存の小地域のストリーミングを使う。[Godot 3D rendering limitations](https://docs.godotengine.org/en/stable/tutorials/3d/3d_rendering_limitations.html)

完了条件は、249%と250%、399%と400%の往復で地形の位置と色が飛ばず、600%・800%で細部がにじみすぎず、パン中にも継ぎ目・欠落・ちらつきがないこと。

## 手順5 水と線を地表に合わせる

海は暗い青灰色を基調にし、浅い場所へだけ少し明るい色を混ぜる。現在の岸距離による着色と波模様を使い、広い白い泡帯や強い鏡面反射で陸地を圧迫しない。実水深がない場所の浅瀬色は見た目の推定として扱う。

川は森林より読み取りやすい低彩度の青で表し、線幅を画面倍率に合わせる。参考ゲームに見える川の太さや形をそのまま転用せず、本作の水系データと既存の地表投影を使う。

道路は既存接続のまま、柔らかい土色で描く。六角形と道路の200%以上の表示条件を保つ。六角形の金線は地形の明暗を読む妨げにならない太さと濃さで比較する。

境界の発光は、線の芯と周囲の弱い光を分けて調整する。本作の家色・選択状態を維持し、参考画面の赤い境界へ全域を統一しない。光を強くして谷や道路を隠すことを避ける。

完了条件は、通常のゲーム画面で川・道・六角形・家色が読み取れ、境界を隠しても山地の形が残ること。

## 手順6 霞を最後に加える

地表の改善後、立体表示の遠い側へだけ青灰色の霞を少量加える。試作では最大混合率5〜12%から始め、平面表示では弱めるか無効にする。地表を完成させる前に霞を強くすると、細部がぼやけた理由が判別しにくくなる。

現行は固定投影の2D地図であり、画面の上側というだけで実際のカメラ距離を表しているわけではない。試作では表示範囲と投影に対応する遠近の係数を明示し、HUDや家紋には霞を掛けない。高度や日照の影と、霞の色を分けて調整する。

雲は参考画面に見えたが、最初の採用対象は霞までとする。雲を試す場合は低密度で、道路・奉行所・選択地点を長く覆わず、地形の明暗比較を邪魔しないようにする。

完了条件は、遠景に奥行きを感じ、400%以上の手前の地表が霞でぼやけず、情報の文字と家紋が鮮明であること。

## 手順7 山の形に不足が残った場合の対応

照明と色を改善しても、稜線の輪郭が粗い、斜面が大きな三角形に見える、尾根と谷の立体感が不足する場合に限り、表示メッシュを改善する。

既存方式を使うなら、表示用の高さをより細かい格子で試し、地表、海岸、川、道路、境界、六角形、クリック逆変換を同じ地表定義へ揃える。地形の画像だけを細かいメッシュへ貼り、線や選択を古い面へ残さない。現行の投影は高さの勾配を制限して逆変換を一意に保っているので、その条件も再検証する。

任意の視点回転、山同士の遮蔽、カメラ移動による見え方の変化まで求める場合は、別の小地域で3D地形メッシュの試作を行う。本作の座標から頂点・UV・地表法線を作り、カメラと光を揃えて比較する。UIは画面側に維持し、地表線とクリックには新しい投影・逆変換を用意する。

3Dへの移行は色画像の交換だけでは済まない。現在の固定投影で目標の見た目に十分近づけば、その結果を採用する。参考ゲームがどの方式を使っているかを断定して移行を決めない。

## 全国への適用と検証

小地域で採用した設定を固定し、生成設定・入力ハッシュ・出力ハッシュ・配色・光の向き・細部の強度を記録する。その後211地域と遠景41画像へ展開する。描画の改善で標高原本、道路探索データ、承認済み陸地を上書きしない。

| `scripts/main/main_map.gd` | 追加資産の受け渡しとストリーミング。既存の倍率範囲を維持 |

### 生成と書き出しの順序

以下は現行のコマンドを基準にした実装時の手順。試作の資産構成が増えた場合は、対応する生成・取り込み・容量計上も追加する。

```powershell
# 小地域の比較後、採用した設定で全国画像を生成
python tools/build_terrain_relief.py
python tools/restyle_terrain.py --workers 4

# PNGをGodotへ取り込み、常駐の遠景を更新
godot_console --headless --path . --editor --quit
godot_console --headless --path . --script res://tools/godot/build_seamless_runtime.gd -- --overview-only

# Windowsリリース版を書き出し
python tools/export_windows_release.py
```

PNGと照明の更新が終わるまではゲームの比較を開始しない。既存の詳細チャンクが参照するPNGの差し替えだけなら、取り込みで画像は更新できる。一方、画像の段階・枚数・形式・ミップ・追加照明・メッシュを変えた場合は、詳細チャンクとランタイムmanifestの資産容量も再生成する。

メッシュと資産構成を変更した場合は `build_map_runtime.gd`、`build_seamless_runtime.gd`、`build_close_detail_runtime.gd`、`build_high_detail_runtime.gd` の生成依存を確認し、通常・近接・高倍率と平面・立体を揃えて作り直す。古い高さの指紋を持つチャンクを残さない。

### 採用条件

1. 丸い樹冠、孤立した草の斑点、岩の割れ目が復活していない。
2. 200%・400%・600%・800%の平面と立体で、同じ地域の植生と稜線が対応している。
3. 主稜線と谷が明暗で読め、影の中の緑が残り、平野が白く飛んでいない。
4. 通常の六角形・道路・家紋・境界を重ねても情報が読める。
5. 隣接タイルと倍率切り替えに継ぎ目・色の段差・模様の飛びがない。
6. パンと倍率往復で地表が欠けず、資産の読み込みと解放が繰り返し暴走しない。
7. 地形の変更に応じてクリック逆変換、川・道路・境界の地表追従を確認する。
8. 採用前後を同じ環境で測り、フレーム間隔のp95・最大値、地図資産量、プロセスとGPUの実メモリを記録する。
9. Windowsリリース版の書き出し結果と起動を確認し、書き出したPCKでも同じ地形画像と倍率切り替えを確認する。

既存の検証は `tests/base_map/test_terrain_materials.py`、`test_terrain_relief.py`、`test_hex_terrain.py`、Godotの `test_close_terrain.gd` と `test_terrain_relief.gd` を変更内容に応じて使う。形状・投影を変更した場合には詳細地形と水系の既存テストも加える。画面の美しさは数値テストだけで判定せず、同条件の比較画像を見て採用する。

## 最初に着手する作業

平野・森林・山地が同時に見える1地域で、照明を分離したB案と、平野の明るさ・森林の深緑を整えたC案を作る。まず主稜線の明暗と平野の色の違いを比較し、連続した細部はその後に少量ずつ足す。この順序で、記号的な模様を使わずに参考画面の精細感へ近づける。


## 2026年9月30日の実施結果

小地域のA 現在、B 照明変更、C 配色変更、D 連続した細部を追加した画像を比較し、Dの光と森林色を調整した設定を採用した。平野・森林・海岸の3地域を平面・立体で確認し、全国の詳細633枚と遠景41枚へ反映した。

採用した照明は環境光0.38、拡散光0.68、斜面の起伏強調3.0。広域の影は最大15%、谷の遮蔽は最大8%とした。照明は生成時に線形色で合成してPNGへ焼き込み、ゲーム中の全国照明画像の再乗算を廃止した。描画用DEMの法線には世界座標0.09単位の平滑化半径を使った。

森林の基本色はRGB 64 99 68、草地は158 176 108、乾いた草地は179 170 119、岩は153 148 127。細部は世界座標0.65単位と0.30単位の連続した濃淡だけを使い、丸い樹冠・独立した斑点・割れ目は作らない。具体的な設定と生成コード・入力のハッシュは `data/derived/detail_map/manifest.json` の `texture_parameters` と `texture_sources` に記録した。

各詳細地域の最高解像度から通常・近接画像を制作時に縮小し、1032・1548・2064pxの完成済みPNGを使用する。実行時に高解像度画像を縮小して代用しない。補間は線形を維持し、ミップマップは今回追加していない。

海と川を低彩度の青灰色、道路を土色へ調整した。六角形の線の最大不透明度を0.30へ抑え、家色の境界帯は幅7画面ピクセル、不透明度0.55とした。立体表示の遠い側に最大6.5%、高倍率では最大3.25%の霞を掛け、平面表示では無効にした。霞は固定投影における画面内の遠い側を近似する色の合成で、実際のカメラ距離や大気散乱の計算ではない。HUD、家紋、文字へ霞は掛からない。

今回の採用範囲は色・照明・水・線・霞まで。表示メッシュと固定の投影は維持し、雲と3D化は実施していない。元の標高と表示用高さ、陸地の座標変換はハッシュ一致を確認した。道路接続・国郡境界・奉行所の位置は変更していない。

### 描画時間とメモリ

同じ1920×1080画面の3地域巡回で、変更前と変更後を測定した。各表示で読み込み完了後に60フレームを測り、12表示のp95と最大値のうち最大の値を下表へ記載する。GPUの機種はNVIDIA GeForce RTX 4060、Godot 4.7.2、Compatibility描画。他のゲームやアプリも起動していたため、隔離した性能保証値ではない。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| フレーム間隔p95の最大 | 51.27ms | 21.51ms |
| フレーム間隔の最大 | 59.17ms | 24.28ms |
| プロセスのワーキングセット最大 | 3249.6MiB | 1979.3MiB |
| プロセスのプライベートコミット最大 | 6484.8MiB | 3962.6MiB |
| GodotのGPU割当監視値の最大 | 2976.5MiB | 1725.5MiB |

この巡回では、最も遅い表示区間のフレーム間隔が改善した。一部の表示には1ms未満の増加もあり、測定のばらつきと区別した継続的な改善を保証するものではない。上のメモリ値はゲーム全体であり、320MiBの地図ストリーム管理予算とは別の値。管理対象の資産量は各表示で予算内であることを検査した。キャッシュの履歴などでも値は変わるため、差のすべてを配色変更の効果とは解釈しない。

変更後はWindowsのGPU Process Memoryカウンターも取得し、対象プロセスの専用メモリ最大1424.4MiB、共有メモリ最大691.2MiBを記録した。両者の最大は同時刻とは限らない。変更前はWindowsのGPUカウンターを取得していないため、実GPUメモリの前後差は断定できない。カウンターの配列取得はMicrosoftの [PdhGetFormattedCounterArrayW](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetformattedcounterarrayw) に従う。

### Windowsリリース版の最終確認

書き出したPCKでは、実際に表示した高倍率テクスチャと制作元PNGの画素一致、3地域の平面・立体表示、200%・400%・600%・800%と画像段階の切り替えを確認し、失敗0件。ゲーム内の描画時間を測定してから画像照合を行い、照合用資産を測定中に保持しないようにした。

## 2026年10月1日：近景の実形状と色・照明の分離

上記の陰影入りPNG方式を更新し、現在のゲーム用PNGには地表色だけを保存する。通常・近接・高倍率の各画像段階と、樹冠・斑点・割れ目を除去した連続模様は維持する。近景を実標高の間隔2の格子へ細分化し、地形法線と平行光源から照明を描く方式を採用した。カメラは通常75°から800%の15°へ移行し、透視投影・空・霞を使う。

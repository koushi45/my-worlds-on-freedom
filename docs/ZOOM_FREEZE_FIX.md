# スクロール拡大・縮小の停止修正（2026-09-13）

## 原因と修正

郡境の破線描画 `district_layer.gd::append_dashes` で、線分の残りが 0.000001 座標単位未満になると、描画位置を進めずに同じ処理を繰り返していた。ズーム倍率によって破線の長さが変わり、この端数が生じる。メインスレッドの無限ループなので、画面描画と入力処理の両方が停止する。

倍率4、長さ1.5000005の線分で修正前の停止を再現し、外部プロセスから8秒で打ち切った。修正後は微小な残りを消費し、破線の位相を引き継いで終了する。破線の描画・空白の切り替え時も正しい次の位相へ進める。連続ホイール入力の可視領域更新はフレームごとにまとめる。

## 自動ログ

通常起動でも以下のフォルダーに保存する。特別な起動引数は不要。

`%APPDATA%\Godot\app_userdata\My Worlds on Freedom\logs\`

- `map_diagnostics.jsonl`：起動・正常終了、250ms超の遅いフレーム（最大毎秒1件）、資産読み込み失敗、10秒ごとの状態。
- `main_thread_stall`：メインスレッドが2秒以上応答しないと別スレッドが記録する。停止中は同じ停止の記録を繰り返さず、復帰時に `main_thread_recovered` を記録する。
- 状態には倍率、カメラ位置、平面／立体、タイル数、読み込み待ち、資産メモリ、直前のズーム操作と時刻を含む。監視スレッドはロックで保護した状態のコピーだけを使用し、シーンやGPUにアクセスしない。
- `godot.log`：エンジンのエラー・警告・標準出力。世代数は5に制限。

診断ログは書き込みごとにフラッシュする。起動時と2MiB到達時にローテーションし、現在のファイルと過去3世代（`.1`〜`.3`）を保持する。`-- --map-profile` では状態の記録間隔を1秒に短縮する。以前の `map_performance.jsonl` に代わり、状態は各JSON行の `state` に保存する。

問題発生後は、再起動を繰り返す前に `logs` フォルダー全体をコピーして保管する。正常終了の記録がなければ強制終了等を疑えるが、それだけでは原因は断定できない。OS・プロセス全体の停止やディスク書き込み不能時の保存は保証できない。

## 検証

- `test_dash_progress.gd`：修正前に停止する微小端数、ゼロ長線分、9倍率の破線生成に合格。
- `test_detail_zoom.gd`：400%上限、マウス位置の保持、平面／立体の詳細タイル切り替えに合格。
- `test_map_streaming.gd`：静止時の更新抑止、資産容量制限、不要要求の除去等に合格。
- `test_map_diagnostics.gd`：メインスレッドを2.6秒止め、停止中のログ書き込み、直前操作の保存、復帰、容量による世代交代を確認。
- `test_wheel_stress.gd`：RTX 4060の実描画で432回のホイール入力を平面／立体で実行し合格。2フレームを含む計測区間の最大は297ms。すべての操作が無遅延という意味ではない。
- 配布PCKからの同じ432回テストも合格（最大285ms）。実行ファイルを180フレーム起動し、終了コード0と自動ログの開始・正常終了記録を確認。

再発時にテスト自体が止まらないよう、破線とログの回帰テストには外部プロセスの30秒タイムアウトを付けた。`python -m unittest discover -s tests/base_map -p test_zoom_freeze.py -v` で実行できる。

修正版Windowsは `builds/windows-zoom-fix/MyWorldsOnFreedom.exe`。未確定709区画を表示する `Windows Unconfirmed` プリセットで生成。

# 画質を維持するメモリ・CPU負荷削減の調査

調査日：2026年10月2日。対象：調査時点の作業ツリーにあるGodot製ゲーム、Windows／Compatibilityレンダラー。

実装後の変更点・検証結果・800%での実測は [MEMORY_CPU_OPTIMIZATION_RESULTS.md](MEMORY_CPU_OPTIMIZATION_RESULTS.md) を参照。本書の既存実装・容量・予算は調査時点の記録である。

## 結論

優先するのは、**武将一覧の肖像の表示範囲に応じた読み込み、静止中のマーカー再描画の停止、近景地形の生成と素材読み込みの予算管理、HUDの変更時更新**である。画像の解像度や地形の細かさを変えず、不要な保持・計算・再描画を減らせる。

次に、3D地図の描画先の範囲と地形データの保持を見直す。静的地図を描画済み画像として再利用する方式も有力だが、現在の海面アニメーションを維持するため、動的部分の分離が必要になる。

本書はコード、資産定義、既存の計測報告、Godot公式資料を調べた提案書である。今回、新しい実行時ベンチマークや変更前後の画像比較は行っていない。削減率・現在のCPU使用率・メモリピークを実測したものではなく、ボトルネックの順位は追加計測で確定する。ゲーム機能、画像、設定は変更していないため、Windowsリリース版の再ビルド・起動確認は今回の文書作成には適用していない。対策を実装した際は必ず実施する。

## 1. 画質とゲーム仕様を維持する条件

- 地形の標高、三角形、法線、陰影、海面の動き、微細素材、境界線、文字、家紋の見え方を維持する。画面外でも影や遠景に影響する領域は単純に除外しない。
- 実画面の解像度、100～800%の素材段階、ミップマップ、フィルター、現在の視点角・回転を維持する。原寸の専用PNGを読み込み、実行時の画像縮小で代用しない。
- UIアイコンの256／192／128／96／64pxの透過PNGと、各サイズの装飾フレームを維持する。新しいSVGは導入しない。漆黒・金装飾の意匠も変えない。
- 六角形と道路の200%以上での表示、道路の六角形レイヤーへの所属、郡奉行所の所属家の家紋とテーマカラー、城・港をマップに表示しない方針を維持する。
- 開発者モードの実標高による50m等高線、終了時の通常表示への復帰、変更値を表示場所で操作するUIを維持する。
- 日付進行、収入、部隊移動・戦闘、選択とクリック面、現在形式での保存・読み込み結果を維持する。

描画結果を変えない対策を先行する。「ほとんど見分けがつかない」圧縮やLODは、厳密な画質維持と分けて扱う。

## 4. 対策の詳細

### 4.1 武将一覧の肖像を表示中の行だけ読み込む

**確認事項：** [officer_panel.gd](../scripts/game/officer_panel.gd) の `refresh_list()` は検索結果の全件で `Portraits.texture_for(id)` を実行し、`ItemList.add_item()` に肖像を渡している。[officer_portraits.gd](../scripts/game/officer_portraits.gd) の `texture_for()` は同期の `load()` を使う。したがって、画面に数十人しか見えていなくても、全検索結果で存在する肖像が読み込み対象になる。これは「登録した全肖像が起動時に読み込まれる」という意味ではない。

**対策：** 名前・検索索引と肖像を分離し、画面内と前後数行分だけ非同期で読み込む。行を再利用するリスト、または表示範囲外のアイコン参照を外す方式を比較する。検索入力を短い待ち時間でまとめ、入力ごとの全件ソート・全行再作成も減らす。同じ検索条件・並び順では結果ID配列を再利用する。

画質を保つため、表示する肖像の元画像は変えず、画像が必要になる直前に取得する。スクロール方向に先読みし、到着までの空欄・代替画像が頻発しないことも合格条件にする。HUDと人物詳細に表示中の肖像は解放対象から外す。

独自キャッシュだけを空にしても、ItemList・TextureRectが画像を参照していればメモリは解放されない。非表示にしたダイアログの行・詳細画像を保持するか、閉じた際に参照を外すかを明示する。GodotのResourceは参照で寿命が決まるため、同じパスを毎回 `load()` しても常に画像が複製されるわけではない。[公式Resource仕様](https://docs.godotengine.org/en/stable/classes/class_resource.html)、[ResourceLoader仕様](https://docs.godotengine.org/en/stable/classes/class_resourceloader.html)。

**確認：** 全員表示→末尾までスクロール→検索→閉じる→再表示を反復し、Private Bytes／VRAM、開くまでの時間、肖像到着時間、画像参照数を比較する。

### 4.2 静止中のマーカー再描画を止める

**確認事項：** [map_screen_markers.gd](../scripts/map/map_screen_markers.gd) は `_process()` で毎フレーム `queue_redraw()` を呼ぶ。`_draw()` では郡奉行所・拠点・部隊を走査し、投影、文字幅、ラベルの重なり、家紋を計算する。`marker_visible()` は遮蔽判定をキャッシュしているので、静止時に毎回全レイ探索を行うわけではない。それでも走査・文字列処理・描画コマンド生成は繰り返される。

**対策：** カメラ位置・倍率・角度・回転、地形の入れ替え、画面サイズ、所属家・名称・選択、部隊位置が変わったときだけ再描画する。全体の更新契機を集約し、1フレームに複数回変更されても1回の更新にまとめる。静止した地理ラベルと動く部隊を別CanvasItemにすれば、部隊移動中もラベルを再計算せずに済む。

文字幅は「文字列＋フォント＋サイズ」でキャッシュする。カメラが動く場合はラベル配置を更新するが、文字幅は再利用する。ラベル衝突は現在の順序を維持し、空間格子で候補を絞ってから同じ矩形交差判定をする。先に採用されたラベルが優先される規則を変えない。

**確認：** 時間停止・静止中の `_draw()` 回数とCPU時間が減ること、カメラ操作と部隊移動・領主交代・選択直後に表示が追従すること、ラベルの採否が一致することを確認する。

### 4.3 近景地形と素材の要求を共通の予算に含める

**確認事項：** [map_view_3d.gd](../scripts/map/map_view_3d.gd) の近景は、512×1024座標範囲を2座標間隔で生成する。`WorkerThreadPool.add_task()` を直接使い、既存の `map_cpu_jobs.gd` の件数・16 MiB枠には含まれない。完成するとメインスレッドで `ArrayMesh.add_surface_from_arrays()` を呼ぶ。1件の近景ジョブを実行中は次を開始しないが、カメラが既に別地域へ移動した場合でも完成結果を一旦適用してから次を作る構成である。

`terrain_material_set.gd::request()` は1段階につき色4枚・法線4枚の計8件を要求する。保持済み段階は整理される一方、`waiting` にある古い要求は完了するまで残り、地図資産の同時2件・176 MiB枠の対象外である。読み込み失敗が発生した段階も、現在の完了条件では待機から抜けられない。

**対策：** ジョブの一時配列、既存メッシュ、GPU登録用の新メッシュ、素材の読み込み予約を合算して管理する。カメラと素材の世代番号を持ち、古い結果は取得・後始末して描画へ反映しない。不要な「未開始」の要求を捨て、実行中のResourceLoader要求を即座にキャンセルできるとは仮定しない。失敗時は再試行回数を制限し、待機・予約を終了させる。

近景の再生成はチャンク分割と既存チャンク再利用で減らす。法線の計算に必要な周辺標高も読み込み、現在の頂点・法線・境界の形を維持する。GPUへの登録はフレーム予算に従って分ける。非同期化だけでは総CPU仕事量は減らず、登録処理の停止も消えない。不要な生成を減らすことを先に行う。[公式バックグラウンド読み込み](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html)、[スレッドの安全性とGPU同期](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)。

**確認：** 全国をまたぐ連続移動と100→800→100%の高速ホイールで、古い生成・素材要求の数、予約ピーク、GPU登録時間、最終表示の準備時間を比較する。予算に収まっただけで、低い素材段階のまま止まった状態を合格にしない。

### 4.4 HUDを変更時更新へ変更する

**確認事項：** [house_status_hud.gd](../scripts/game/house_status_hud.gd) は0.5秒ごとに `_refresh()` を呼ぶ。全郡を走査し、人口・兵数・治安などを集計し、当主の肖像と家紋、全表示文字列を再設定する。日付が停止していても動く。

**対策：** 家の所属郡IDの索引を持ち、所有変更時に更新する。金銭・兵数・治安・技術・当主・肖像などの変更イベントで集計を失効させ、同じフレームの更新をまとめる。値や文字列が同じならControlへ再設定しない。画像は当主ID・家紋アセットが変わった場合だけ取得する。

ウィンドウの物理サイズ監視は `time_hud.gd` と部隊アイコンにもある。既存のDPI・原寸PNG選択を維持し、共有の表示倍率監視から変更通知できるか調べる。単に監視を止めると `canvas_items` の論理サイズが変わらないリサイズを見逃す。

**確認：** 領主変更、徴兵、収入、研究、当主変更、保存復元、DPI／サイズ変更の直後に表示が一致すること。変更のない停止中に全郡集計が繰り返されないことを確認する。

### 4.5 地形メッシュの生成を制作時へ移し、保持を減らす

**確認事項：** `map_view_3d.gd::_ready()` は全国の遠景メッシュと富士の詳細メッシュを同期生成する。富士詳細は非表示でも起動時から保持される。全国標高は `terrain_vertices.bin` を全読込し、4097×4097×2 = **33,570,818 bytes（約32.02 MiB）**。富士標高は513×513×2 = **526,338 bytes（約0.502 MiB）**。遠景メッシュは513×513頂点で、`terrain_vertices` に頂点配列を別途保持する。調査した同ファイル内では、この配列は最大高さの走査以外に参照されていない。

**対策：** 遠景・富士の頂点・法線・UV・索引を現在と同じ手順で事前生成し、Godotのバイナリ資産へ保存する。入力の標高・投影条件のハッシュを検証する。最大高さは資産のメタデータに保存し、不要なCPU頂点配列を保持しない。富士詳細は可視範囲への接近時に先読みし、地域外では上限付きキャッシュへ戻す。

全国標高32 MiBの分割は後段で検討する。近景・ピッキング・山の遮蔽の問い合わせに必要な標高を同じ精度でチャンクロードする。読み込まれていない地点のクリックが近似面へ落ちる設計は避ける。32 MiBだけを削るために問い合わせやI/Oが増える可能性もあり、常駐方式との実測比較が必要。

`elevation_surface.gd::_init()` は数値標高用PNGをTexture2Dとして読み、`get_image()` と各画素走査で513×513の配列を作る。同じ数値を事前生成したPacked配列から読めば、CPUが使うデータをGPUテクスチャ経由で取り出す起動処理を省ける。既存のfingerprint・投影・クリック結果は一致させる。

**確認：** 起動時間、富士にいない時の保持量、標高の全値、頂点と法線、地形クリック面、富士への初回移動時の準備時間を比較する。資産化はCPU生成を省くが、読み込みとGPU転送の時間は残る。

### 4.6 3D地図の描画先と地図読み込み範囲を見直す

**確認事項：** `map_view_3d.gd::sync()` は地理レイヤーをSubViewportへ描き、3D地表の素材として使う。描画先の式は `size.x+32` と `size.y*3.5+max_height*8+32` に物理画素倍率を掛け、各軸4096pxで制限する。この描画先全体の矩形から `visible_rect` を作るため、地表の実画面に投影されない部分も地図タイル・ベクトルの対象になり得る。サイズはズーム中に固定され、再確保を抑える工夫は既にある。

**対策：** カメラの視錐台、地表、標高範囲から必要な元地図範囲を求める。画面に見える地表と同じ物理画素密度を確保したまま、完全に使われない上下左右を削る。ウィンドウ・姿勢の区分ごとに描画先を事前確保するなど、毎フレームの再確保を避ける。描画先を削る対策と、地図読み込み対象だけを絞る対策は別々に計測する。

参考として4096×4096のRGBA8色バッファ1枚は **64 MiB**。これは寸法から計算した例であり、現行SubViewportの実測VRAMではない。実際の形式、追加バッファ、ドライバ、解像度によって変わる。更新停止だけではこの確保は解放されず、容量削減には寸法・枚数を減らす必要がある。

**確認：** 15～90度の視点、全方位回転、800%、高い山・遠景・海岸で欠けや解像度低下がないこと。元描画先寸法、可視タイル数、描画呼び出し、VRAMを記録する。

### 4.7 静的地図を再利用し、海面だけを毎フレーム動かす

**確認事項：** `map_view_3d.gd::_ready()` の `source_view` は `UPDATE_ALWAYS`。[海面シェーダー](../scripts/map/ocean_texture.gdshader) は `TIME` でUVを動かすため、地理描画先全体を無条件に停止すると海面の動きも止まる。

**対策：** 地形色・郡塗り・境界・道路などの静的合成は、カメラ、選択、所属、読み込み完了、モード変更で更新する。海面は地形の水域マスクを使い3Dシェーダー側、または独立した動的レイヤーで動かす。必要フレームだけ `UPDATE_ONCE` を使う構成を比較する。画面上で参照されている描画先に `UPDATE_WHEN_VISIBLE` を指定するだけでは、静止時の更新は止まらない。[公式SubViewportの更新モード](https://docs.godotengine.org/en/stable/classes/class_subviewport.html)。

マーカー・部隊を別レイヤーにする方針と合わせる。ただし新しい描画先を増やすとVRAMが増えるので、追加の色バッファを作らずに海面を合成する方式も比較する。

**確認：** 同じ時刻・姿勢の海面、海岸の透過と境界、道路、郡選択を画像比較する。海面の動きを保ったまま、静的地図の更新回数と静止時CPU／GPU時間が下がることを確認する。

### 4.8 診断スナップショットを低頻度化する

**確認事項：** `map_diagnostics.gd` は通常起動でも有効で、毎フレーム状態のDictionary、カメラ座標配列、実行中資産のキー配列、Performanceモニター値を作り、Mutex内で共有する。通常ログは10秒ごと、`--map-profile` では1秒ごとだが、スナップショットの作成は毎フレームである。書き込みは既に別スレッドへ移してある。

**対策：** 毎フレームはハートビートとフレーム遅延の最小情報に絞る。詳細状態は100～250msごと、または操作・資産状態の変更時に作る。停止直前の倍率・入力・読込状態を記録し、2秒の停止検出、失敗と履歴は残す。監視・ログを全面無効化して調査能力を失う対策は採らない。

**確認：** 通常起動での診断CPU時間・配列生成回数を比較する。`test_map_diagnostics.gd` など既存の停止検出・ローテーション試験に加え、停止直前情報の鮮度を確認する。

### 4.9 保存・開発者資産・空間索引の追加候補

[game_session.gd](../scripts/game/game_session.gd) の `capture()` は多数の状態を `duplicate(true)` し、保存・読み込み時にも複製する。大きい履歴や部隊が増えたセーブで実測し、変更可能な状態の一貫したスナップショットを1回だけ作り、JSON文字列や保存後の中間参照を早期解放する。別スレッドで共有辞書をそのまま読む方式は避ける。保存頻度・履歴・ゲームルールは変更しない。リリース前なので旧形式の移行・互換試験は不要で、現在形式での保存復元を検証する。

等高線レイヤーは既に最初の切り替え時に生成される。`developer_tools.gd::set_contour_mode()` は戻った後にhideするので、最初から常時ロードされるとは扱わない。一度使った大きい等高線画像などは、モード終了時に解放するか小さい再訪キャッシュへ戻すか比較する。道路ネットワークは通常の移動にも使われるため、開発者モード専用だと思って全解放しない。

郡・奉行所・拠点の走査は空間索引で候補を減らす。既存の `marker_visibility` キャッシュを維持し、カメラ移動時の高コストな地形レイ判定をまず計測する。索引とキャッシュの追加はメモリを増やすため、CPU削減と保持量を両方比較する。

## 5. メモリの見積もりと計測の注意

| 対象 | 計算・確認値 | 解釈 |
|---|---:|---|
| 全国標高バイナリ | 32.02 MiB | ファイル実サイズ。PackedByteArrayに全読込する |
| 富士標高バイナリ | 0.502 MiB | ファイル実サイズ。これとは別にメッシュがある |
| 遠景頂点だけ | 513×513×12 ≒ 3.01 MiB | float32のxyzを仮定した配列容量。GPUや索引・法線は別 |
| 近景の配列一式 | 257×513×32＋256×512×6×4 ≒ 7.02 MiB | 頂点・法線・UV・索引の理論値。旧メッシュ・新メッシュ・転送用コピーは別 |
| RGBA8描画先の例 | 4096×4096×4 = 64 MiB | 色バッファ1枚。実形式と実際の確保量は未計測 |
| 800%素材8枚の例 | 1254²×4×8×4/3 ≒ 63.99 MiB | 全てRGBA8・全ミップを仮定。実フォーマットは要計測 |

素材段階の寸法は100%=192px、200%=384px、400%=768px、600%=1024px、800%=1254px。[素材manifest](../assets/map/materials/manifest.json)と一致する。`grass_800.png.import` は調査時点でLossless、ミップ生成あり。63.99 MiBは全8枚がRGBA8だった場合の概算で、実測や全素材形式の断定ではない。

RAM、VRAM、キャッシュ予算、ファイル容量を混同しない。Private Bytesはプロセス専用のコミット量、Working Setはその時点で物理メモリ上にあるページ。GodotのMEMORY_STATICやGPUモニターはOS全体・ドライバの全確保を網羅せず、リリースでは取得できない値もある。各指標を単純に足して「総メモリ」としない。

キャッシュの上限を下げるだけでは、再訪の読み込みとCPUが増える。表示中の資産を優先し、再訪のヒット率、読み込み待ち、最終品質の到着を見ながら調整する。モード切り替え・GPU更新時の旧資産と新資産の同時保持、ロード中の予約もピークに含める。

## 6. 今回の条件で先行しない対策

| 対策 | 理由 |
|---|---|
| 全画像をJPEG・非可逆WebPへ変更 | PNG容量が小さくなっても非圧縮VRAMは減らない。透明度と画質にも影響する |
| 全素材へVRAM圧縮を強制 | 圧縮誤差があり、画質無変更を保証できない。数値標高には不適切 |
| CompatibilityのままHigh Quality圧縮を有効化 | 公式仕様ではCompatibilityでこの設定は無効。BC7等が使える前提で見積もらない |
| ミップマップ・法線・影・霞・海面を無効化 | ちらつき、質感、照明、動きが変わる |
| 解像度・描画先の画素密度・最大ズームを下げる | ユーザーの画質維持条件に反する |
| 一律30fpsへ制限 | 空間的画質は保てても、操作・動きの滑らかさが変わる |
| 全仕事を並列化 | 総CPU時間や一時メモリを増やす場合がある。GPU登録やSceneTree操作にも制約がある |
| 未使用資産をPCKから除けばRAMも同じだけ減ると考える | パッケージ容量とロード済み資産の常駐量は別。配布容量の対策としては有効 |

画像圧縮とCompatibility制約の根拠：[Godot公式画像インポート仕様](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_images.html)。既存の圧縮済み地図画像を戻す提案ではなく、追加の圧縮を画質無変更の対策として扱わないという意味である。

WindowsのFPS上限は別途確認する。現行 `main_map.gd` はAndroidの30fpsと `--map-fps=30/60` を明示するが、Windowsの通常上限はVSync・プロジェクト・実行環境も含めて調べる。モニターの既存表示頻度を超える余分なフレームが出ているなら抑制を比較できる。60Hzと高リフレッシュレートの環境を一律60fpsへ落とさない。[公式Engine.max_fps](https://docs.godotengine.org/en/stable/classes/class_engine.html)。

`OS.low_processor_usage_mode` は静止画中心の状態で使えるが、現在のTIMEによる海面と地図更新を維持する条件では無条件適用しない。最小化・非表示時の描画抑止は別候補とし、ゲーム時間の継続・再開と入力応答を維持して比較する。[公式OS仕様](https://docs.godotengine.org/en/stable/classes/class_os.html)。

## 7. 実装前後の比較手順

### 計測するもの

1. Windowsリリース実行ファイルの実際の描画プロセスPIDを記録する。起動用ランチャーを測らない。CPU・GPU・RAM・画面寸法・物理倍率・VSync・FPS上限・Godot版・資産ハッシュを固定する。
2. CPUはプロセスCPU時間の増分、平均使用率、ピーク、主要スレッドの実行時間を記録する。CPU全体の10%だけではメインスレッドの飽和は判定できない。コア数と集計方式を併記する。
3. フレーム時間はp50／p95／p99／最大／100ms超の割合、入力から応答まで、最終品質が表示されるまでを記録する。FPS上限に張り付いている場合でも、CPU仕事時間とCPU秒／操作は比較する。
4. Private Bytes／Working Setは100～250ms間隔で記録し、GPU専用・共有メモリも別に測る。短いピークを取り逃す可能性を記載する。地図予算、予約、素材段階、描画先寸法、ノード・資産数も記録する。
5. 処理別に `_draw()`、HUD集計、近景生成、メッシュ登録、素材ロード、マーカー遮蔽、保存スナップショットの時間と回数を測る。診断を有効にした比較と通常起動の比較を分ける。

Godotのプロファイラーで関数ごとのCPU時間を調べ、必要ならOS側のスレッド・待機・GPU転送も追う。闇雲な変更より、同じ操作を測って支配的な処理を減らす。[公式CPU最適化指針](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)。

### 操作シナリオ

| シナリオ | 確認する問題 |
|---|---|
| タイトル→新規開始→全国図 | 起動時の同期生成・ロードとピーク |
| 時間停止・静止を60秒 | マーカー、HUD、診断、地理描画先の余分な仕事 |
| 時間進行・静止を60秒、部隊あり／なし | 描画削減とゲーム進行の分離 |
| 100／200／400／600／800%、角度15～90度、回転 | 素材要求、描画先、地形とクリック面の一致 |
| 九州→近畿→富士→関東を12巡 | 不要ジョブ、キャッシュ再訪、メモリ蓄積 |
| 全武将一覧、検索、末尾移動、人物詳細、閉じるを反復 | 一覧全件の肖像保持と解放 |
| 領主交代、徴兵、研究、月・年進行 | HUD・家紋・郡色の更新漏れ、日付イベントの負荷 |
| 等高線へ切り替え→終了→再開 | 開発者資産の保持と通常表示復帰 |
| 大きい現行セーブの保存→タイトル→読み込み | 保存中ピーク、状態一貫性、解放 |
| リサイズ、DPI変更、最小化と復帰 | 原寸PNG、描画先再確保、表示欠け |

各シナリオは初回とキャッシュが温まった再訪を分け、独立した実行で最低3回比較する。長時間試験は30分以上追加し、同じ地域・同じ画面へ戻った後の増加傾向も確認する。今回の調査時点ではゲームの実行プロセスは見つからず、既存プロセスの使用率を観測した値はない。

既存の [benchmark_map.gd](../tests/base_map/godot/benchmark_map.gd) は出発点として使えるが、100／400%中心で、武将一覧・600／800%・現行近景の完了を十分に網羅しない。`main_map.gd::has_pending_map_work()` の条件には3D近景ジョブと素材waitingが明示されていないため、「準備完了」の条件を拡張してから最終品質の到着時間を測る。古い測定結果との単純比較は避ける。

### 画質・機能の合格条件

- 同じ画面サイズ・物理倍率・姿勢・素材段階の画像を比較する。海面TIMEや部隊を同じ時刻に固定した比較と、通常の動きの確認を両方行う。
- 静的描画を減らす変更は、文字、輪郭、家紋、道路、奉行所、細部素材に新しい差がないことを目視と画像差分で確認する。画像差が出た場合は原因を解消し、単に小さいから許容とはしない。
- メッシュ資産化・分割は標高、頂点、法線、境界、ピッキングを照合する。画面外除外は低い角度、遠方の山、影、回転で欠落がないことを確認する。
- CPU／メモリの削減だけでなく、再訪と最終品質到着、入力応答が悪化していないことを確認する。未測定の削減率を成果として記載しない。
- 機能やUIを変更した最後に、[Windows書き出しツール](../tools/export_windows_release.py)など既存手順でWindowsリリース版をビルドし、EXE／PCKの生成、配布資産での表示、実行ファイルの起動を確認する。

## 8. 着手順

まず現行Windowsリリース版で静止・一覧・高速ズームの基準を取る。次にマーカーの変更時再描画と一覧の肖像保持を個別に改善し、それぞれの効果と画質を比較する。その後HUD、近景と素材の予算統合、地形の事前生成へ進む。

描画先範囲の見直しと海面分離は、これらの比較で静的地図の描画が主要負荷と判明した場合に進める。全国標高の分割や保存形式の変更は、実測でメモリの主要部分やピーク原因になった場合に行う。これにより、画質を維持できる小さい変更から効果を確認し、大きい設計変更の必要性を判断できる。

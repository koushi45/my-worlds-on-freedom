# 毎秒8日に向けた速度改善の実装記録

実装日：2026年10月5日。対象：[改善方針](GAME_SPEED_8_DAYS_PER_SECOND_PLAN.md)。

## 変更内容

| 方針 | 実装 |
| --- | --- |
| P0 計測 | 索引・キュー選択・所有変更・表示形状更新の時間分布と回数を追加。探索の着手待ち、ワーカー処理、結果回収待ちを分離。時計の観測した停止区間と、入力・バックログ上限で破棄した時間を記録 |
| P1 索引 | 領地・外交は状態が変わった場合だけ再構築。軍勢所属・出陣武将と、位置・脅威を分離。空間区画は移った部隊だけ更新し、同一区画内の接近も実距離で判定 |
| P1 重複計算 | 研究効果を研究状態ごとに再利用。直接の研究配列変更と保存データの置換も検出し、共有する結果は読み取り専用にする |
| P1 射撃判定 | 同時射撃中の軍勢位置を再利用し、射程外の部隊を外交・射撃性能の評価前に除外。9本の射線で共通の部隊位置・差分も共有。対象の走査順、味方への遮蔽・誤射、同時ダメージ適用を維持 |
| P1 出陣判断 | 出陣だけを調べる仕事は、当日の出陣済み・部隊上限・武将不足・上位3郡の兵力／兵糧不足を先に判定。出陣不能なら目標候補と経路の評価を省く。既存部隊への命令は別の仕事で継続 |
| P2 キュー | 全体ソートと先頭削除を、優先度・登録順のヒープと定数時間の取り出しに変更。3日締切を維持。登録順を保存し、読み込み後も同優先度の順序を保つ |
| P3 所有変更 | 投影済みの領地装飾形状を再利用し、同一フレームの変更家の表示更新をまとめる。論理的な所有更新は即時。制圧時と次の世界更新で同じ所有変更を二重に失効させない |
| P3 追いつき処理 | 実時間からの移動・戦闘の追いつき量をフレームごとに制限。60 FPSで約0.5日、30 FPSで約1.0日を上限とし、未処理分は既存の有限バックログへ保持。内部の移動・戦闘ステップは変更しない |
| P3 過渡負荷の保持 | バックログ上限を2日から8日へ変更。8倍速で実時間1秒相当の有限保持とし、現行保存の検証上限も時計の定数を参照。停止・最小化時は保持分を破棄 |
| P4 探索 | 道路スナップショットを外交変更で作り直さず、道路変更で更新する。政治的通行条件の再利用枠を拡大。プレイヤー自動命令も疎な障害物を再利用し、移動費用をセルから直接計算 |
| P4 上限 | 通常の探索枠を2件から4件へ変更。進行中と失効済み未終了を合わせて制限。経路キャッシュは最大2048件／概算8MiB、主体別通行条件は最大256件 |
| P5 予算 | 通常はフレーム間隔の35%、0.5日以上の遅れがある間は最低60%。最小1.5ms・最大20msで制限し、遅れが減ると通常配分へ戻す。比較用に `--cpu-budget`・`--route-workers` を追加 |

家・軍勢を画面外だから更新しない処理や、日次更新・戦闘の間引きは追加していない。必須処理と緊急判断、探索の締切を維持する。新しいキューの順序情報は現行の仕事データに含め、保存・読み込みを検証する。

所属索引は軍勢の生成・合流・武将変更・消滅の版番号でも更新する。帰還による即時消滅が汎用の `changed` 通知を発しないケースでも、消えた軍勢・武将が索引や戦力評価に残らない。

思考予算は1件の仕事の終了後に確認するため、月初更新などの不可分な仕事が20msを超える場合はある。これはフレーム全体や入力遅延の厳密な上限ではない。追いつき中の追加配分は日次規則・緊急判断・探索の締切を撤廃するものではない。

2日上限の途中計測では、処理集中時に3～10日分を破棄していても、後半の10秒窓は8日/秒、終了時バックログは0日へ戻る回があった。継続的な能力不足と過渡負荷を区別し、再計算削減とフレーム分割を実装した上で保持上限を8日へ変更した。上限拡大だけを速度改善として扱わず、進行率・10秒窓・終了時保持分を確認する。詳細計測が無効な配布版の主測定では破棄カウンターは更新されないため、ゼロという出力だけで未破棄と判定しない。

配布版の診断では、移動の上限を30 FPSで0.8日とすると、必須更新が終わっていても日付を完了するためにもう1フレーム必要になった。戦闘開始時の処理集中を解消する能力が不足し、60秒平均が7.786日/秒となった。思考配分を増やして射撃の重複計算を減らした段階でも7.629日/秒だったため、実時間に応じた分割上限を最大1日に変更した。内部の1/30日刻みの移動・射撃計算は保ち、日次の必須処理を待つ条件も維持している。これらは個別の診断回であり、固定シードでも探索完了順と戦況が異なるため、変更単独の改善率とはしない。

## 計測の読み方

`jobs`には内訳も含まれる。`index:*`、`scheduler:*`、`ownership:*`、`army_phase:*`を親処理へ二重加算しない。`route:queue_wait`と`route:pickup`は待ち時間、`route:worker`はワーカー内の経過時間であり、メインスレッドのCPU時間へ合算しない。並列処理の経過時間合計は実時間を超え得る。

時計の`wait_usec`は従来の呼出し時の理由集計。`blocked_wall_usec`は観測した理由の開始・変更・解除から求めた区間で、フレーム単位の観測誤差がある。OSによる実行待ちと計算時間を厳密に区別するCPUサンプリング値ではない。

`discarded_backlog_days`は保持上限からあふれた日数、`discarded_input_usec`は長い入力時間の制限分。形状キャッシュは投影方式が変わると破棄する。再利用で処理時間を減らす代わりにCPUメモリを増やすため、Godotのメモリ監視値も併記する。

## 採用を見送った変更

探索枠を8件へ増やす比較と、外交の当事者だけ経路を失効させる比較を行った。枠の増加だけでは再探索が増えて遅いケースがあり、部分失効では再判断の連鎖を含む進行の悪化が見られた。今回は4件と全国失効を採用し、所有・道路・外交の変更時の保守的な検証を維持する。

予算は18%、24%、30%、35%の短い比較と60秒測定を段階的に行った。30%では通常6回中1回が7.942日/秒、35%固定の戦闘配置では最初の10秒に処理が集中し、後半は8日/秒へ戻っても60秒平均が7.893日/秒だった。遅れがある間だけ45%とする比較でも最小7.939日/秒だったため、追加配分を50%へ調整した。それでも出陣候補を繰り返し作る重い戦況では7.829日/秒の回があり、予算増加だけに頼らず、出陣不能な場合の事前判定を追加した。これらは途中の実装と可変の戦況を含む診断値であり、各変更単独の因果的な速度向上率ではない。

月次処理の途中状態を保存する分割、全国更新の全面並列化、固定ステップの変更、GDExtensionへの移植は追加していない。まず研究効果などの重複計算を減らし、残る長い処理を実測する方針とした。戦略候補の継続カーソルは既存の方式を維持する。

### 性能とリリース

通常・戦闘開始時12部隊のWindows配布版で、60／30 FPS・各60秒×3回の全12回が7.95日/秒以上となった。最小値は7.991日/秒。全回で保存データと軍勢・武将・位置索引の検証に成功した。

条件：Core i7-12700F、RTX 4060、Godot 4.7.2公式Windowsリリース、OpenGL Compatibility、NVIDIA 596.36。ウィンドウ表示、VSync無効、固定シード1546、各回の開始状態を復元し2秒待ってから計測。詳細プロファイルは無効。別テスト・ビルドは同時実行しなかったが、作業開始前からの別のゲームプロセス2件は停止していないため、完全に隔離した性能測定ではない。

### メモリと配布確認

形状などの再利用はメモリとの交換である。開発版の途中測定ではGodot静的メモリが約751MiBで、以前の約473MiBから増えていた。ただしこれは最終配布版と同条件の測定ではない。公式リリースでは静的メモリ監視値が0で取得できず、最終版の使用量を0MiBとは判定しない。GPU描画バッファ値は生データに記録した。低メモリ端末とAndroidでの性能は未確認。

`python tools/export_windows_release.py`によるWindowsリリースの書き出しは終了コード0、エラー・資源不足検出なし。`python tools/verify_speed_release.py`で通常起動、35日分の必須更新と途中状態・最終状態の保存／復元、CPU計画・軍勢・外交の復元を確認した。最終配布テストではスクリプトエラー・機能失敗・終了時Resourceエラーはなかった。別の診断回と回帰テストには既存の終了時解放警告があり、検証ツールは既知のResource終了診断だけを別欄へ記録し、それ以外のエラーは失敗とする。

# 内政・国家運営シミュレーション構築 作業手順書

作成日：2026-09-24  
対象：1546年開始シナリオ。以下は今後の実装順序と検証条件であり、未実装機能を実装済みとは扱わない。

## 1. 到達目標

プレイヤーが家の方針を選び、郡・家臣・周辺勢力に働きかけると、月次・年次で状態が変わり、次の選択肢とリスクが変わるゲームを作る。EU4のような国家運営の手応えは、数値の種類を増やすことより、**限られた資源をどこへ使うかという選択、遅れて現れる結果、他勢力の反応**から生む。本作では1546年の戦国日本、家・郡・武将を中心に独自のループを作る。

最初の遊べる到達点は、1家を選んで5年間進め、課税・治安維持・開発・家臣待遇・研究を選択でき、財政悪化と騒乱を避けながら国力を伸ばせること。外交・戦争を加える前に、この内政だけで選択と結果が成立する状態を完成させる。

### 循環の設計図

```text
人口・開発・治安・施設
  → 金銭・兵糧の生産
  → 俸禄・維持費・備蓄・政策費
  → 開発・治安対策・研究・動員への投資
  → 人口・開発・忠誠・治安・軍事力の変化
  → 収支と反乱・飢饉・対外行動の選択肢が変わる
```

どの数値にも「増える原因」「使い道」「不足時の結果」「プレイヤーに見える予告」を用意する。初期値や効果量は史実の確定値と混同せず、ゲーム用の調整値として記録する。

## 2. 現状の接続点と欠けている接続

| 要素 | 現在の実装 | 次に必要な接続 |
|---|---|---|
| 時間 | `game_clock.gd` が日付を進め、月初に処理を呼ぶ | 月次処理の順序を一か所で管理し、結果を記録する |
| 郡・人口・開発 | `governance_registry.gd` が郡人口、農業・商工業開発度、基礎治安を保持 | 人口の自然増減、収容力、被害、開発投資、治安による生産変化 |
| 金銭・兵糧 | `district_economy.gd` が金銭を毎月、兵糧を9月1日に家へ加算し、担当武将の政治力で開発が進む | 食糧消費・備蓄不足、政策費・維持費、郡ごとの収支内訳、赤字の帰結 |
| 技術力 | `retainer_management.gd` が統治・外交・軍事を月次生成。`technology_tree.gd` は統治技術力を使う統治・農業研究を実装 | 外交・軍事の使い道、研究選択の競合、維持費と副作用。商業研究は項目未設定 |
| 治安・忠誠 | 技術による治安補正、俸禄・任命・威信による忠誠と月初の離反がある | 税・飢饉・軍の駐屯・統治担当と治安の相互作用、俸禄未払いの結果 |
| 外交・戦争 | 開始時の同盟・敵対・中立、威信のイベント用メソッド、道路と拠点の表示データがある | 交渉・条約・開戦・軍隊・補給・占領・講和の実行処理 |
| 操作画面 | 通常画面は地図中心。詳細な開発用UIは `--developer-ui` で生成 | 通常画面で自領・収支・政策・警告を操作できる導線 |

`docs/TECHNOLOGY_TREE.md` にある人口成長・常備兵・施設費・災害軽減は計算補助までで、対応する実行処理はない。`docs/LOYALTY.md` の戦闘離反フックも、部隊と戦闘の実装待ち。現行の俸禄支払いは金銭を0で止めるため、不足額と未払いによる忠誠変化を表現できない。郡の開発担当設定は現状、対象家への所属や同時任命数の制約を十分に扱わない。これらを新要素の前に設計上の接続課題として扱う。

なお、1546年開始データと1582年を対象に作られた拠点・道路の資料が同居する。拠点の存在年、通行可否、施設効果をゲームへ使う際は1546年時点の状態を確認し、将来の拠点・道を開始時の国力として数えない。対象郡数も文書に固定せず、現行シナリオの有効IDから取得する。

## 3. 全工程に共通する実装規則

1. **状態の持ち主を決める。** 家は金銭・兵糧・技術力・外交関係、郡は人口・開発・治安・施設・被害、武将は所属・役職・忠誠、軍は兵数・所在・兵糧・士気を持つ。地図形状や史料台帳は実行時状態と分離する。
2. **月次処理を一本化する。** 既存の `day_advanced` 接続を踏まえ、月初の順序を明文化する。例：前月の政策と状態を確定 → 収入・収穫 → 消費・俸禄・維持費 → 不足処理 → 治安・人口・開発 → 忠誠・騒乱 → 技術力 → AIの翌月方針 → 通知。9月の収穫と1月の年次処理は月次の中に配置し、同じ日付で二重実行しない。
3. **支払いの結果を残す。** 費用を先に検証し、実行できない命令は拒否する。自動費用は支払額と不足額を記録し、不足の帰結を適用する。金銭・兵糧の残高だけを0に丸めて不足を消さない。
4. **同一ルールを全勢力へ適用する。** 人間だけを優遇する収入・治安計算を避ける。AIの意思決定は別の層に置く。
5. **数字の由来を追えるようにする。** 郡・家の画面で現在値、前月差、収支の内訳、次回見込み、主な補正を表示する。端数処理、上限、効果の加算・乗算順は仕様に固定する。
6. **現行セーブ形式のみ確認する。** リリース前のため旧形式からの移行と旧形式との互換性チェックは作らない。形式を変えたら現行形式の保存、再起動後の読込、同日からの再開を検証する。

## 4. 実装順序

### 工程0：遊びの単位と数値仕様を固定する

- [ ] 主要判断を「課税方針・食糧配分・開発投資・治安対策・人事・研究」に絞り、各判断の費用、便益、遅延、逆効果を一枚の仕様表にする。
- [ ] 課税は金銭増と治安低下、開発は現在の支出と将来の収入増、治安対策は維持費と騒乱抑制、家臣待遇は俸禄と忠誠、研究は統治技術力と長期効果を交換する設計にする。
- [ ] 月、収穫年、5年の評価指標を決める。例：家の純収支、兵糧備蓄月数、郡別治安、人口、離反件数、研究数。目標値は仮置きして調整記録に残す。
- [ ] 課税率、食糧必要量、人口成長率などの係数をデータ化し、単位と適用時点を記す。現在の収入式を変更する場合は初期バランスも再計算する。

**完了条件：** すべての資源に獲得方法・用途・不足時の帰結があり、同じ月の計算順序を図と仕様表から再現できる。

### 工程1：シミュレーション基盤と収支台帳

- [ ] `game_clock.gd` の日付通知から呼ぶ月次進行役を設け、`district_economy.gd`、`retainer_management.gd` などへの呼出順をそこへ集約する。高速進行やロード後に月初を飛ばさず、重複実行もしない。
- [ ] 家・郡の収支を `source_id / amount / reason / date` で記録し、金銭・兵糧・技術力の入出を追えるようにする。郡別の内訳を家の合計へ集計する。
- [ ] 開発担当の所属・在職・同時担当・領有の検証を追加する。所有者変更時には担当、政策、見込み収入を再評価する。
- [ ] 収入と俸禄の計算を収支台帳へ通し、未払いを検出する。まず既存動作を台帳に載せ、金額を変える調整は次工程へ分ける。
- [ ] セーブへ政策、残高、必要な進行状態を保存する。表示用の月次内訳は必要なら再計算・再生成できる設計にする。

**完了条件：** 12か月進めた家の残高差が台帳の入出合計と一致し、保存して同日から再開しても翌月結果が一致する。

### 工程2：内政の最小循環を完成させる【最優先】

1. **食糧と人口。** 郡人口に対する食糧消費、家の備蓄、収穫の季節性を実装する。兵糧不足は人口・治安・忠誠へ段階的な悪影響を与える。人口増減は食糧、治安、郡の収容力に依存させ、急増・急減を防ぐ上限を置く。既存の「人口台帳」の即時+10%は研究効果として不自然な循環を作るため、人口把握や税収効率への置換も含め仕様を再検討する。
2. **課税と治安。** 家または郡に低・標準・高の課税方針を用意する。税収の増減、治安、人口流出、反乱危険度へ効果をつなぐ。基礎治安と研究補正を区別し、基礎値は月次で悪化・回復する。治安対策に金銭と適任武将を使えるようにする。
3. **開発と施設。** 自動的な担当武将の開発進行は残しつつ、金銭・兵糧を使う投資命令を加える。農業は収穫量、商工業は月次金銭へ主に寄与させる。施設は最初は農業・市場・治安の少数に絞り、建設費、期間、維持費、効果を明示する。`technology_tree.gd` の施設費補正を実際の建設処理へ接続する。
4. **俸禄と忠誠。** 未払い月を記録し、忠誠と離反判定へ反映する。威信・役職・俸禄・担当郡の状態が忠誠へどう効くかを一覧化し、離反が突然起きないよう翌月の危険を示す。治安悪化が統治担当の忠誠や独立リスクへ及ぶ経路を決める。
5. **騒乱。** 治安と飢饉が続いた郡に騒乱段階を設ける。初版は生産停止・金銭損失・治安対策の選択までとし、戦闘部隊を必要とする反乱軍は工程5で追加する。自治や帰属未詳の郡について、課税・命令の可否を別に決める。

**完了条件：** 5年間の試遊で「増税 → 短期収入増 → 治安悪化 → 生産や人口への損失」と「投資 → 短期赤字 → 長期収入増」が数値と画面で確認でき、放置時と介入時の結果が異なる。

### 工程3：技術力を意思決定へつなぐ

- [ ] 統治技術力で研究する既存ツリーの項目と前提関係を整理する。発動しない効果を持つ技術は、対応処理を作るまでは研究不可または説明に「効果未接続」を明示する。商業技術の空ツリーも、項目を設計するまで選択不可とする。
- [ ] 外交技術力の消費先を「交渉準備、情報収集、条約維持」などに、軍事技術力の消費先を「編制、補給、築城・攻城研究」などに定める。技術力を使うだけで万能な効果を得られないよう、金銭・時間・人材なども条件にする。
- [ ] 技術の効果を数値計算の単一箇所で適用し、領有変更、研究直後、ロード直後でも同じ結果にする。研究済みの家と、郡に残る恒久的な変化を区別する。
- [ ] インフレを避けるため、月次生成量、上限、研究費、研究完了までの年数を複数規模の家で比較する。1つの正解手順で全研究を即座に終えられないようにする。

**完了条件：** 3種類の技術力すべてに実際の使用先があり、研究の有無で内政・外交・軍事の少なくとも一つの結果が変わる。

### 工程4：外交を相手のいるシステムにする

- [ ] `game_session.gd` の家ペア関係を基礎に、関係値、同盟、通行、停戦、期限、条約履行を定義する。初期関係が未設定の家を敵として扱わない。
- [ ] 交渉命令に外交技術力・金銭・使者武将・所要時間を結び、相手の利益、威信、国境、既存条約から受諾率を計算する。成功・失敗理由を表示する。
- [ ] 威信の既存フックを実際の行動へ接続する。条約違反や不当な開戦の損失、官職や勝利の利得を同じイベント経路で処理する。
- [ ] AIも交渉を提案・拒否し、プレイヤーが軍事行動なしで安全や利益を得る選択肢を作る。

**完了条件：** 外交技術力を使った交渉が相手の判断で成否を分け、条約と威信が次の交渉に影響する。

### 工程5：兵糧を使う軍事・領土変化

- [ ] 募兵可能人口、常備兵、兵数、士気、維持費を定義する。徴兵は労働人口・生産・治安を削り、平時にも兵の維持費が発生する。既存の「常備兵」技術補正を動員上限や維持費へ接続する。
- [ ] 兵糧の軍への補給、輸送・補給線、季節、道路、城・港を使った移動を実装する。1582年用の推定道路は1546年の通行保証とせず、採用可否と海上接続を明示してから経路計算へ使う。
- [ ] 宣戦理由、開戦、部隊移動、戦闘、包囲、占領、講和、領有変更を小さな順に作る。戦闘力には武将能力・技術・地形・士気・補給を用い、兵数だけで結果を決めない。
- [ ] 領有変更時に税収先、統治担当、郡の治安、駐屯、家臣忠誠、地図表示を更新する。既存の戦闘離反フックは部隊データができてから接続する。

**完了条件：** 1つの隣接郡をめぐる戦争で、募兵から講和まで進み、補給不足と長期占領が内政へ返る。講和後の保存・再開で領有・部隊・経済が一致する。

### 工程6：事件・AI・通常画面を仕上げる

- [ ] 飢饉、洪水、台風、当主交代、家臣の不満、国境紛争などを、発生条件・確率・対策・後続効果を持つ事件として追加する。災害軽減技術は実際の被害計算へ接続する。史実の出来事とゲーム上の変動を区別する。
- [ ] AIの優先順位を「食糧と財政を維持 → 騒乱を抑える → 開発・研究 → 外交 → 戦争」とし、難易度は判断精度で調整する。AIだけの資源生成で帳尻を合わせない。
- [ ] 通常画面に家の収支・兵糧備蓄・技術力・危険郡の一覧、郡の命令、研究、外交、通知履歴を設ける。`--developer-ui` の調査機能はそのまま残してよいが、遊ぶための操作は通常画面に置く。
- [ ] 警告には「何が」「いつ」「なぜ」起きる見込みか、対処の費用と見込み効果を表示する。数字は月次台帳と同じ計算結果を使う。

**完了条件：** 通常起動だけで5年の内政と1回の外交・戦争を完結でき、重要な損失は発生前に予告される。

## 5. 工程ごとの検証と調整

| 検証 | 合格基準 |
|---|---|
| 決定性 | 同じ開始データ・命令・乱数種なら月次結果が一致する。月の途中で保存・読込しても次回処理を重複しない |
| 収支保存 | 家の期首残高 + 収入 - 支出 = 期末残高。郡合計と家合計が一致し、資源を無から作らない |
| 境界値 | 人口0、兵糧0、金銭不足、治安0/100、開発上限、研究済み、担当武将不在、郡移転を処理できる |
| 効果の接続 | 技術・政策・施設を有効にした場合としない場合で、仕様通りの対象値だけが変わる |
| 継続性 | 1年・5年・20年の自動進行で残高の無限増殖、全家の即時破綻、人口の異常増減がない |
| 遊びやすさ | 小・中・大勢力で同じ政策が常に最善にならず、破綻原因と回避策が画面で分かる |

新しい仕組みごとに、その仕組みを実際に通る少数のGodotテストを追加する。既存の `tests/base_map/godot/test_start_session.gd`、`test_technology_tree.gd`、`test_retainer_management.gd`、`test_loyalty.gd` は回帰確認に用いる。セーブ形式を変更した工程では `game_session.gd` の現行形式で保存・読込・再開を検証する。大規模な調整は1つの仮想家だけで決めず、複数規模の家で年次指標を比較し、係数変更と結果を記録する。

## 6. 推奨する最初の実装単位

まず工程0と1を終え、工程2から **「課税方針、食糧消費、治安の月次変化、未払い俸禄」** を1本の縦断実装として作る。必要な状態をセーブし、通常画面で家と選択郡の見込み・前月差を表示する。この単位が5年間安定して遊べてから、施設、外交、軍事を順に追加する。

主な参照先：`scripts/game/district_economy.gd`、`scripts/game/retainer_management.gd`、`scripts/game/technology_tree.gd`、`scripts/game/governance_registry.gd`、`scripts/game/game_session.gd`、`scripts/main/main_map.gd`、`docs/TECHNOLOGY_TREE.md`、`docs/LOYALTY.md`、`docs/GAME_TIME.md`。
